# 새 아이디어/기능 반영 절차

## 문제
프로젝트 진행 중 새로운 아이디어가 계속 생길 수 있다. 그때마다 로드맵이 뒤죽박죽되지 않으려면, 아이디어를 받는 쪽(사용자)과 반영하는 쪽(Claude) 모두가 같은 절차를 따라야 한다.

## 절차 (4단계)

### 1. 말씀만 해주시면 됩니다
완성된 스펙일 필요 없다. "이런 거 하고 싶어" 정도의 러프한 아이디어면 충분하다. 이번 지도 홈 화면 아이디어처럼.

### 2. 도메인 매핑 먼저
아이디어를 코드로 바로 옮기지 않고, 먼저 판단한다:
- **기존 도메인(`BUSINESS_RULES.md` Part 0)의 규칙 확장인가?** (예: 이번 지도 홈 화면 = 이미 있던 Discovery 도메인의 역할 확장)
- **완전히 새로운 도메인이 필요한가?** (예: 처음 나온 "직원 친절도 평가" = Staff 도메인 신설)

이 판단 결과를 `BUSINESS_RULES.md`의 도메인 정의/규칙표에 먼저 반영한다. 여기서 조작 불가능성, 데이터 노출 범위 같은 무결성 원칙도 함께 정리한다 (이번의 "방 코드 비노출" 같은 것).

### 3. 로드맵 영향 분석 + 재정렬 제안
- 이미 **완료되고 병합된 Phase는 절대 다시 건드리지 않는다** — 새 아이디어는 항상 "아직 시작 안 한 Phase" 구간에만 삽입된다.
- 우선순위를 당길지/그대로 둘지, 그 이유를 명시해서 제안한다 (예: "필요한 하부 데이터가 이미 준비돼 있어서 지금 시작 가능" 같은 근거).
- 결과물은 항상 로드맵 문서 갱신본 하나로 정리한다 (`ROADMAP_V2.md`처럼 버전을 올리되, **항상 최신 버전 하나만 기준으로 삼는다** — 옛 버전끼리 서로 다른 순서를 말하면 혼란만 커짐).

### 4. 승인 후에만 코드 작업 시작
설계 문서 갱신 → 사용자 확인/승인 → 그다음에만 실제 코드 구현에 들어간다. 이 순서를 건너뛰고 바로 코드부터 짜지 않는다.

## 원칙 요약

| 원칙 | 이유 |
|------|------|
| 완료된 Phase는 재작업하지 않는다 | 이미 병합된 코드를 흔들면 회귀 위험이 생긴다 |
| 로드맵은 항상 최신 버전 하나만 유지 | 여러 버전이 공존하면 "지금 뭐가 맞는 순서인지" 헷갈린다 |
| 도메인 정의부터 갱신, 코드는 그다음 | 설계 없이 코드부터 짜면 나중에 도메인 경계가 뒤엉킨다 |
| 진행 중인 Phase 도중 아이디어가 오면, 지금 끼어들지/끝내고 반영할지 먼저 확인 | 작업 중간에 방향이 계속 바뀌면 아무것도 안 끝난다 |

## 참고
이 절차 자체는 이번 지도 홈 화면 아이디어를 반영하면서 실제로 밟아본 순서를 그대로 문서화한 것이다 (`BUSINESS_RULES.md` §2.6 갱신 → `ROADMAP_V2.md` 작성 → 사용자 확인 대기).
