# ADR-0005: 3개 가설(A/B/C)의 검증 순서 확정

- **상태**: Accepted
- **날짜**: 2026-08-10 (같은 날 A+C 동시검증으로 수정 — 아직 병합 전 PR 안에서의 수정이라
  별도 ADR을 새로 만들지 않고 이 문서를 직접 갱신함)
- **관련 문서**: `ROADMAP_V2.md` "핵심 가설과 MVP 로드맵" 섹션, ADR-0004

## 맥락

ADR-0004에서 정한 핵심 가설("손님이 매장에서 앱을 실제로 켜서 쓴다")은 여러 가설 중 하나일
뿐이었다는 게 드러났다. 사용자가 두 개를 추가로 제기: "사장님이 AI 운영 리포트를 필요로
하는가"(운영자 대상), "외부 사람들이 실시간 분위기 데이터를 원하는가"(잠재 손님/외부 대상).
이 서비스는 손님↔운영자 양방향 구조라 가설도 원래 하나가 아니었다. 세 가설을 어떤 순서로,
어떻게 검증할지 기준이 없어서 MVP 범위를 정하기 어려운 상태였다.

## 결정

세 가설을 A(손님이 앱을 켜서 쓴다) / B(사장님이 AI 운영 리포트를 필요로 한다) / C(외부인이
실시간 분위기 데이터를 원한다)로 명명한다.

1. **A와 C는 함께 검증한다.** 원래는 C(지도/Discovery)가 A의 결과물(실시간 분위기 데이터)에
   의존하니 A를 먼저 단독으로 보고 C는 나중에 열려고 했다(지도를 코드는 두고 접근만 막는
   게이팅). 근데 C는 이미 코드로 다 구현되어 `main`에 있어서, 굳이 그걸 숨기는 로직
   (리다이렉트/플래그)을 새로 만드는 것 자체가 이 시점엔 불필요한 엔지니어링이라고 판단 —
   막지 않고 처음부터 A/C를 함께 연다
2. **단, A 지표와 C 지표는 반드시 따로 관찰한다.** A가 완전히 실패하면(리액션 사용이 거의
   없으면) 지도에 보여줄 실시간 데이터 자체가 비어서 C 결과도 같이 해석 불가능해질 위험이
   있다. 완화책: 방 화면 리액션 사용(A)과 지도/매장상세 조회·클릭(C)을 처음부터 별도로
   트래킹해서, 최소한 "A는 됐는데 C가 안 됐다" 정도는 구분할 수 있게 한다
3. **B는 A/C와 분리해서, 그것도 실제 구현 전에 먼저 값싸게 검증한다** — B(AI 운영 리포트)는
   지금 있는 운영자 대시보드가 AI가 아니라 순수 통계 화면이라 완전히 새로 만들어야 하는
   기능이다. A/C가 만들어내는 실제 데이터가 있어야 리포트에 넣을 내용이 생기므로 A/C 이후로
   미루고, 실제로 만들기 전에 파일럿 사장님들에게 직접 물어보거나 가짜 버튼(fake door)으로
   반응을 보고 신호가 긍정적일 때만 실제 구현에 들어간다

## 버린 대안

- **세 가설을 한 번에 다 검증할 수 있는 통합 MVP를 만든다** (B까지 포함) — 결과가 나와도
  원인을 특정할 수 없어 폐기. B는 여전히 분리 유지
- **A만 먼저 단독 검증, 지도는 게이팅해서 숨김** (최초 결정) — 지도가 이미 다 구현돼 있는
  상태에서 그걸 숨기는 로직을 새로 만드는 엔지니어링 비용이, 얻는 해석상 이득(완전히 깨끗한
  단일 가설 실험)보다 크다고 판단해 폐기. 대신 지표 분리로 리스크를 완화(위 2번)
- **B를 A/C와 병행 개발** — B는 A/C가 만들어내는 실제 데이터가 있어야 의미가 있는 리포트라,
  그 데이터 없이 병행하면 속이 빈 기능을 만들게 됨. 폐기

## 후속 작업

- v0.1.0(가설 A+C, 지도 게이팅 없이 전체 기능) 구현이 최우선 — `MILESTONES.md`/`ROADMAP_V2.md` 참고
- A 지표(방 화면 리액션)와 C 지표(지도/매장상세 조회)를 분리 관찰할 수 있도록 파일럿 리뷰
  시점에 반영 (구체 방법은 파일럿 착수 시 결정)
- 가설 B는 코드 작업 없음 — 파일럿 사장님 인터뷰/가짜 버튼 설계는 A/C 검증 이후 논의
