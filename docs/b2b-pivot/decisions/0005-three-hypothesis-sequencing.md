# ADR-0005: 3개 가설(A/B/C)의 검증 순서 확정

- **상태**: Accepted
- **날짜**: 2026-08-10
- **관련 문서**: `ROADMAP_V2.md` "핵심 가설과 MVP 로드맵" 섹션, ADR-0004

## 맥락

ADR-0004에서 정한 핵심 가설("손님이 매장에서 앱을 실제로 켜서 쓴다")은 여러 가설 중 하나일
뿐이었다는 게 드러났다. 사용자가 두 개를 추가로 제기: "사장님이 AI 운영 리포트를 필요로
하는가"(운영자 대상), "외부 사람들이 실시간 분위기 데이터를 원하는가"(잠재 손님/외부 대상).
이 서비스는 손님↔운영자 양방향 구조라 가설도 원래 하나가 아니었다. 세 가설을 어떤 순서로,
어떻게 검증할지 기준이 없어서 MVP 범위를 정하기 어려운 상태였다.

## 결정

세 가설을 A(손님이 앱을 켜서 쓴다) / B(사장님이 AI 운영 리포트를 필요로 한다) / C(외부인이
실시간 분위기 데이터를 원한다)로 명명하고, 다음 순서로 검증한다:

1. **A가 최우선** — B와 C 둘 다 A에 의존한다(손님이 안 쓰면 공유할 데이터도, 리포트에 넣을
   데이터도 없음). A 없이는 B/C 검증 자체가 불가능
2. **A 검증 후 C를 B보다 먼저** — C(지도/Discovery)는 이미 구현되어 있어 게이트만 풀면 되는
   저비용 실험이고, B(AI 리포트)는 아예 새로 만들어야 하는 고비용 실험이라 비용이 낮은 쪽을
   먼저 시도
3. **B는 실제 구현 전에 인터뷰/가짜 버튼(fake door)으로 먼저 검증** — AI 리포트를 실제로
   만들기 전에, 파일럿 사장님들에게 직접 물어보거나 가짜 버튼으로 반응을 보고 신호가
   긍정적일 때만 실제 구현에 들어간다

세 가설을 한 MVP에 동시에 넣지 않는다 — 실패 시 어느 가설이 틀렸는지 구분할 수 없는
뒤섞인 실험(confounded experiment)이 되기 때문이다.

## 버린 대안

- **세 가설을 한 번에 다 검증할 수 있는 통합 MVP를 만든다** — 이미 만든 기능(운영자
  대시보드, 지도)이 많아서 유혹적이지만, 결과가 나와도 원인을 특정할 수 없어 폐기
- **B를 A/C와 병행 개발** — B는 A가 만들어내는 실제 데이터가 있어야 의미가 있는 리포트라,
  A 없이 병행하면 속이 빈 기능을 만들게 됨. 폐기

## 후속 작업

- v0.1.0(가설 A) 구현이 여전히 최우선 — `MILESTONES.md`/ROADMAP_V2.md 참고
- 가설 C는 v0.2.0(지도 게이트 해제)으로 이미 스코프됨, 코드 추가 불필요
- 가설 B는 코드 작업 없음 — 파일럿 사장님 인터뷰/가짜 버튼 설계는 A 검증 이후 논의
