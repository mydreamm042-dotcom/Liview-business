# MySTAR/Liview B2B 로드맵 v2

## 이 문서의 위치
초기 설계 초안이 Phase 순서를 정의했지만(지금은 삭제됨, `README.md` 참고), 새 아이디어(지도 기반 홈 화면, 좌석 배치, 손님 케어)가 그 순서에 영향을 주므로 **이 문서가 Phase 순서와 각 Phase 세부 스코프에 대해 유일한 기준**이다.

이 문서는 계속 갱신된다 (v2 안에서 개정). 새 아이디어가 들어올 때마다 새 파일을 또 만들지 않고, 이 문서 하나를 최신 상태로 유지한다 (`CHANGE_INTAKE_PROCESS.md` 원칙).

## 지금까지 반영된 새 아이디어

### ① 지도 기반 홈 화면 + 실시간 핫플레이스 탐색
> "Liview 기본 화면 = 지도. 하단 UI: 입장하기 / 실시간 핫한 가게 찾기 / 방만들기. 방 코드는 제공하지 않는다 (원격 참여 악용 방지)."

새 도메인이 아니라, 이미 설계해둔 **Discovery 도메인**의 역할이 커진 것 (부가 기능 → 앱의 기본 진입점). 핵심 신규 규칙: **Discovery 화면은 방 코드/QR을 절대 노출하지 않는다** (`BUSINESS_RULES.md` §2.6).

### ② 좌석 배치도(자리배치) + 좌석별 실시간 HOT 표시 + 운영자 좌석 이동
> "가게 입장 시 자리배치도로 이동해 좌석 선택. 좌석마다 HOT 탭 여부 표시. 운영자가 손님 좌석을 드래그(모바일 롱프레스 2초)로 옮기면 참여자 화면에도 반영됨 — 손님이 잘못 앉았을 때 사장님이 고치는 용도. 좌석마다 착석 경과시간 타이머도 표시."

새로운 **Seating 도메인**을 도입 (`BUSINESS_RULES.md` §2.7). 좌석 선택, 운영자의 좌석 강제 이동(+실시간 참여자 화면 반영), 착석 경과시간 타이머까지 확정됐다.

### ③ 손님 케어 (경고 메시지 / 쿠폰 지급)
> "자리배치도에서 손님을 우클릭(모바일=터치)하면 경고 메시지(자유 입력)/쿠폰(매장 등록 카탈로그 중 선택) 지급 가능. 앞으로 기능이 더 늘어날 가능성 높음."

새로운 **Guest Care 도메인**을 도입 (`BUSINESS_RULES.md` §2.9). Seating과 트리거 화면은 같지만(자리배치도), "위치"가 아니라 "그 손님에게 무엇을 하는가"를 다루는 별개 도메인이다 — 액션이 계속 늘어날 걸 감안해 확장형으로 설계. **주의**: 기존 Reaction 도메인의 `warning`(참여자 간 익명 자제 시그널)과 이름이 겹치므로, 신규 기능은 "운영자 경고 메시지(Operator Alert)"로 명확히 구분한다.

### ④ 매장 고정 QR + 영업 시작/종료 + 입장 비밀번호 + 위치 반경 제한
> "사장님이 원하는 건 '방 만들기'가 아니라 매장을 한 번 등록하면 고정 QR을 받는 것. 오늘 영업 시작/종료 버튼으로 세션을 열고 닫음. 방 코드는 필요 없음. 대신 QR을 사진 찍어 유포하는 원격 도배를 막기 위해 (1) 운영자가 켜고 끌 수 있는 입장 비밀번호(형식 제한 없음), (2) 위치 반경 제한(벗어나면 입장 불가, 입장 후 이탈 시 자동 퇴장)."

**이건 Phase 1에서 이미 만든 BUSINESS 방 생성/입장 방식에 대한 정정이다** — 새 Phase로 옆에 추가하는 게 아니라, "방 만들기 화면에서 매번 이름 입력 → 코드로 입장"이라는 원래 설계가 실제 술집 운영 방식과 안 맞는다는 걸 바로잡는 것이다. 다행히 Venue 도메인 자체(1 venue : N rooms, Phase 1에서 이미 만든 구조)는 이 흐름에 그대로 들어맞아서, 큰 스키마 변경 없이 "입장 방식"과 "세션 생성 방식"만 바뀐다:
- Venue 도메인 확장: `join_password_enabled`/`join_password`/`geofence_radius_m` (`BUSINESS_RULES.md` §2.2)
- Room 도메인 확장: 고정 QR 입장(코드 불필요), 영업 시작=방 생성, 영업 종료=방 마감 (`BUSINESS_RULES.md` §2.1)
- Participant 도메인 확장(신규): 위치 반경 제한 — 입장 시 + 입장 후 지속 (`BUSINESS_RULES.md` §2.3)

Phase 8.5가 Phase 9보다 먼저인 이유: 어차피 홈/방만들기/입장 화면을 이번에 재설계하는데, 리디자인 전에 PERSONAL 관련 화면을 먼저 걷어내야 "지울 화면까지 디자인 반영하는" 낭비가 안 생긴다. Phase 9 → Phase 10 순서인 이유는 대시보드 화면도 리디자인 대상이라, 새 디자인 셸을 먼저 입히고 그 위에 필터 기능을 얹는 편이 재작업이 적기 때문이다. 기존에 대기 중이던 쿠폰 지급/Phase 7/각종 미확정 세부 항목(§"다음 단계" 참고)은 이 세 Phase 이후로 순연한다.

**Phase 9 스코프 확정 + Phase 9.5 신설 (2026-07-22)**: 사용자가 피그마 스크린샷(홈 지도/지역 랭킹/매장 상세) 전달 → 리뷰 과정에서 "순수 시각 변경만 다룬다"던 Phase 9의 기존 확정 사항이 정정됨 — 실제로는 신규 기능(실제 장소 검색, 지역별 TOP10 랭킹, 세션 유무 무관 전체 매장 지도 표시, 매장 상세 바텀시트의 비참여자 공개 프리뷰)이 다수 포함된 것으로 확인됨. 이 중 "구독 중인 매장만 기능이 작동한다"는 요구사항은 UI 변경이 아니라 완전히 새로운 도메인(결제/구독)이라 **Phase 9.5로 분리** — PG(결제대행사) 계약/심사는 개발 공수와 무관하게 리드타임이 길 수 있어 병행 착수를 권장한다.

**Phase 1.5는 예외적으로 이미 병합된 Phase 1 코드 일부(BUSINESS 방 생성/입장 API)를 고친다.** "완료된 Phase는 재작업하지 않는다"는 원칙(`CHANGE_INTAKE_PROCESS.md`)의 예외인데, 새 기능 추가가 아니라 **실제 운영 방식과 안 맞는 설계를 사용자가 직접 바로잡은 것**이기 때문이다. Phase 1의 다른 부분(venues 테이블, room_type, closed 상태)과 Phase 2(브랜딩)는 그대로 둔다.

## Phase 1.5 상세 — 매장 고정 QR + 영업 시작/종료 + 입장 비밀번호 + 위치 반경 제한

### 스코프
1. `venues` 테이블에 `join_password_enabled`/`join_password`/`geofence_radius_m` 추가
2. `POST/DELETE /api/venues/[id]/session` — 영업 시작/종료 (기존 "방 만들기"의 BUSINESS 경로를 대체)
3. `GET /api/venues/[id]/session` — 매장의 현재 세션(영업 중 여부) 조회
4. `POST /api/venues/[id]/join` — 고정 QR 기반 참여자 입장. 비밀번호(켜져 있으면) + 위치 반경 검사를 통과해야 기존 입장(재입장 복귀/신규 생성) 로직으로 이어진다
5. 참여자 입장 로직(재입장 복귀/동시 요청 레이스 처리)을 공통 헬퍼로 분리해, 기존 코드 기반 입장(PERSONAL, 무수정)과 신규 매장 기반 입장이 같은 규칙을 공유하도록 함
6. 운영자 설정 화면에 비밀번호 ON/OFF 토글 + 입력 필드 추가
7. 참여자용 매장 랜딩 화면(`/v/[id]`) — 위치 권한 요청 → (비밀번호 필요시) 입력 → 닉네임 입력 → 입장 → 기존 방 화면으로 이동
8. 입장 후 지속 위치 체크 — 반경 이탈 시 자동 나가기(기존 나가기 API를 자동 트리거)

### 확정
- `rooms.code` 컬럼은 삭제하지 않고 내부 URL 슬러그로만 계속 사용 (참여자에게 노출/요구만 안 함) — 스키마 변경 최소화
- 비밀번호는 평문 저장, 형식 제한 없음, 운영자 본인에게만 조회 노출
- 위치 반경 기본값 50m

### 미확정
- 위치가 등록 안 된 매장은 반경 검사를 건너뛰는 것으로 처리(입장 제한 없음) — 의도와 맞는지 확인 필요
- 입장 후 지속 위치 체크 주기(초 단위) — 배터리/정확도 트레이드오프, 초기값은 구현하며 정함
- 비밀번호 오답 시 재시도 제한(브루트포스 방지) 필요 여부

## Phase 3 상세 — Liview 홈 (지도 + 실시간 탐색)

### 스코프
1. `get_live_hot_venues()` 함수 (완료 — `supabase/migrations/0002_discovery.sql`, `0004_discovery_geofence_radius.sql`)
2. `GET /api/discover/venues` — 위치 기반 실시간 HOT 매장 목록 (카테고리 필터, 정렬)
3. 홈 화면 교체 — `src/app/page.tsx`를 지도 기반으로. 하단 3버튼: 입장하기 / 실시간 핫한 가게 찾기 / 방 만들기
4. 매장 카드/상세 화면 — 실시간 HOT·만족도, opt-in 매장만 채팅 프리뷰. **방 코드/QR 절대 미표시**
5. 공개 채팅 최소 기능 — `venues.public_chat_enabled` 토글 + 읽기 전용 API
6. **(추가, Phase 1.5 이후 반영) 지도 마커 탭 → 바텀시트 상세** — 별도 페이지 이동 대신 지도 위에 매장 상세를 띄우고, `/v/[id]`로 이동하는 "입장하기"(반경 밖이면 비활성화 + 거리 안내)와 외부 지도 "길찾기" 버튼을 추가. `/discover` 리스트 페이지는 그대로 유지 (BUSINESS_RULES.md §2.7 "지도 마커 상세" 참고)

### 확정
- 지도 SDK: **카카오맵** (JavaScript SDK, 무료 호출량으로 충분, 국내 가게 검색 정확도 높음)
- 바텀시트의 입장하기는 `/v/[id]`로 이동만 시키고, 실제 검증은 그 화면의 기존 join 로직이 그대로 담당 (새 검증 경로를 만들지 않음)
- 반경 밖일 때 입장하기 버튼은 비활성화 + "OOOm 떨어져 있어요" 안내 문구 (에러 클릭 방식 아님)

### 미확정
- Discovery 홈을 PERSONAL 참여자에게도 그대로 보여줄지

## Phase 4 상세 — 좌석 배치 + 운영자 좌석 이동 + 손님 케어

### 왜 Phase 3 바로 다음인가
- 참여자 흐름상 "지도에서 매장 발견 → 실제 방문 → QR 입장 → **좌석 선택**"으로 자연스럽게 이어지는 다음 단계다.
- Seating과 Guest Care는 같은 화면(자리배치도)에서 동작하므로 한 Phase로 묶어 구현하는 게 효율적이다.

### 스코프 — Seating (확정)
1. `venue_seats` — 매장 좌석 목록(라벨), 운영자가 구성 (설정 화면에서 추가/삭제, Phase 2 설정 패턴 재사용)
2. `participants.seat_id` + `seat_assigned_at` — 참여자가 선택/배정된 좌석과 배정 시각
3. 참여자용 자리배치도 화면 — **좌석 선택은 필수** (선택 전엔 방 화면 진입 불가), 좌석별 실시간 HOT 표시(파생), 착석 경과시간 타이머(파생)
4. **운영자 좌석 이동** — 운영자 화면에서 특정 참여자의 좌석을 변경 → 해당 참여자 화면에도 반영 (기존 3초 폴링 재사용, 신규 realtime 채널 불필요)

### 스코프 — Guest Care (이번 Phase 범위)
5. 자리배치도에서 손님 우클릭(모바일: 터치) → 액션 메뉴
6. **운영자 경고 메시지** — 자유 텍스트 입력 후 특정 손님에게 발송 (`operator_alerts` 신설, `reactions.warning`과는 별개 테이블/개념). 참여자 화면엔 확인 버튼이 있는 **모달**로 표시된다
7. 액션 로그는 감사 이력으로 보존 (삭제 안 함)

### 이번 Phase 범위 밖 (다음으로 연기)
- **쿠폰 지급** — 등록 화면/데이터 구조, 수령 확인/사용 방법이 모두 미확정이라 사용자가 이번엔 제외하기로 결정. 사양이 확정되면 별도 Phase로 진행

### 미확정 — 스펙 대기
- 좌석 이동 시 착석 타이머가 리셋되는지 (현재는 "리셋"으로 해석해뒀음 — 확인 필요)
- Guest Care에 추가될 예정이라고 언급된 "그 외 기능들" — 구체화되는 대로 계속 반영

### 영향받지 않는 것
- PERSONAL 방에는 좌석/손님케어 개념 자체가 없다 (Venue가 없으므로)
- 기존 QR 입장 흐름은 그대로, 입장 "다음" 단계로 좌석 선택이 추가될 뿐
- Reaction 도메인의 기존 `warning`(자제 시그널) 로직은 전혀 건드리지 않는다

## Phase 4.5 상세 — 운영자 정식 회원가입/로그인

### 왜 예외적으로 지금 삽입하는가
Phase 1.5와 같은 이유다 — 새 기능이 아니라, `operator_owner_token`(브라우저 임의 토큰)으로 운영자 신원을 대신해온 임시 방식이 실제 정식 출시 조건(계정 복구, 프랜차이즈형 다중 매장, 향후 소셜 로그인)과 안 맞는다는 걸 사용자가 직접 지적해 바로잡는 것 (`CHANGE_INTAKE_PROCESS.md` 예외 규정).

### 스코프
1. `operators` 테이블 — `auth.users`(Supabase Auth) 1:1 프로필. 비밀번호 해시/세션은 Supabase Auth에 위임하고 이 테이블은 표시 이름/연락처/역할만 갖는다
2. `venues.owner_id` FK 추가 (nullable, `operator_owner_token`은 전환 기간 동안 유지)
3. 이메일+비밀번호 회원가입/로그인 화면 (`/operator/signup`, `/operator/login`)
4. 기존 `operator_owner_token` 매장을 로그인 계정에 연결하는 "매장 인증 전환" 1회성 플로우
5. 운영자 관련 API 라우트 전부를 `operator_token` 파라미터 방식에서 Supabase Auth 세션(`auth.uid()`) 기반으로 전환
6. BUSINESS 방의 `isHost` 판정을 `venues.owner_id = auth.uid()` 기준으로 재구성 (PERSONAL 방의 `host_session` 판정은 그대로 유지)

### 확정
- 인증 수단은 **Supabase Auth** (자체 비밀번호 해시 테이블 대신) — 이유: 향후 구글/카카오 로그인을 붙일 계획이 있고 Supabase가 둘 다 기본 지원하므로 재작업이 없음
- `operator_owner_token` 컬럼은 즉시 삭제하지 않고 전환 기간 동안 유지
- PERSONAL 방의 `host_session`(익명 세션)은 이 리팩토링과 무관, 변경 없음

### 미확정
- 이메일 인증(확인 메일) 필수 여부 — 데모/테스트 단계에서는 편의상 꺼둘 수 있음 (Supabase 대시보드 설정)
- 한 매장에 여러 운영자(공동 운영)를 붙이는 기능 — 지금은 1(운영자):N(매장)만 지원, 다대다가 필요해지면 별도 조인 테이블로 확장

## Phase 5 상세 — 운영자 대시보드

### 왜 지금인가
> "사장님들이 지난날들 운영했던 운영 데이터를 제공해주고 싶어. 인스타그램이나 유튜브에 있는 프로페셔널 대시보드 같은 기능을 제공해주고 싶어."

Operator Analytics 도메인(`BUSINESS_RULES.md` §2.10)은 Phase 1부터 "위 모든 도메인의 데이터를 읽기 전용으로 재가공해 대시보드를 제공한다"고 이미 예정돼 있었지만 스코프가 비어있었다. 이 요청으로 처음 구체화된다.

### 스코프
1. `get_operator_dashboard(p_venue_id, p_days)` — 매장의 지난 영업일(마감된 BUSINESS 방) 전체를 한 번의 DB 호출로 집계하는 함수 (`get_reaction_summary`/`get_live_hot_venues`와 같은 RPC 패턴)
2. `GET /api/venues/[id]/dashboard` — 운영자 본인 매장만 조회 가능 (`requireOperator` + `verifyVenueOwner`)
3. 운영자 설정 화면에 "운영 리포트" 진입 카드 추가
4. 대시보드 화면 — 개요 통계 카드, 일별 추이(참여자 수/평균 만족도/HOT 밀도) 라인 차트 3종, 요일별 평균 참여자 막대 차트, 베스트 영업일 랭킹(HOT 밀도·만족도·참여자 수 각 Top 3)

### 확정
- **원본 데이터만 재가공한다** — 새로 추적을 시작해야 하는 지표(리뷰, 직원 평가, 이벤트 타임라인 등 아직 없는 도메인)에는 의존하지 않는다. 오직 이미 존재하는 `rooms`(마감된 BUSINESS 방)/`participants`/`reactions`/`operator_alerts`만 집계한다 — Operator Analytics 도메인의 "원본 데이터 미수정" 원칙과 같은 결로, 존재하지 않는 데이터를 추론해서 채우지 않는다
- **HOT 밀도**는 방 화면의 실시간 HOT %(감쇠 시뮬레이션)와 다른, 대시보드 전용 파생값이다 — `그 세션의 HOT 탭 총 개수 / 손님 수`로 정의한다. 실시간 지표를 그대로 재현하려면 초 단위 감쇠 시뮬레이션을 서버에서 다시 돌려야 해서 비용이 크고, 지난 영업일 비교에는 "밀도"만으로 충분하기 때문
- **재방문 손님**은 같은 매장의 서로 다른 방(영업일)에 동일한 `session_token`(참여자 익명 세션)이 다시 나타난 경우로 정의한다 — 새로운 개인식별 트래킹을 추가하지 않고 이미 있는 값만으로 판정
- 운영자 본인("사장님" 닉네임으로 입장한 운영자 참여자 행, §2.8/2.9 "운영자가 손님으로 입장")은 손님 지표(참여자 수, 재방문 등)에서 제외한다
- 일별 추이 그래프는 최근 90일로 제한하지만, 개요 통계(총 영업일수 등)와 베스트 영업일 랭킹은 전체 기간 기준이다 — 그래프 가독성과 "역대 최고 기록"의 의미를 모두 지키기 위함

### 미확정
- Staff/Review 도메인(Phase 6/7)이 구현되면 대시보드에 직원 친절도·검증 리뷰 지표를 추가할지 — 지금은 그 도메인들이 아직 없어 제외
- 대시보드 데이터를 CSV/이미지로 내보내는 기능 — 요청 시 별도로 추가

## Phase 5.5 상세 — 요일별 영업시간 + 마감시간 기반 자동 마감

### 왜 예외적으로 지금 삽입하는가
Phase 1.5/4.5와 같은 이유 — 새 기능이 아니라, "영업 시작=방 생성"(Phase 1.5)이 전제했던 "운영자가 영업 종료를 제때 누른다"는 가정이 실제로는 자주 깨진다는 걸 사용자가 지적해 바로잡는 것이다. 운영자가 종료를 안 누르면 다음날 영업이 전날 방에 그대로 합쳐져 Operator Analytics(Phase 5)의 일별 데이터가 오염된다.

### 논의 과정에서 기각된 대안들 (기록용)
- **참여자 활동량 기반 추론**("N시간 조용하면 자동 마감") — 운영자/직원이 참여자로 위장 입장해 활동을 만들면 감지가 무력화됨. 기각
- **활동 데이터를 아예 삭제** — 운영자가 버튼을 안 누른 것과 손님의 실제 상호작용 데이터는 별개 문제. 실제 데이터를 지우는 건 이 앱 전체의 "BUSINESS 이력은 삭제하지 않는다" 원칙과 충돌. 기각
- **일정 시간마다(예: 매시간) 무조건 강제 마감** — Vercel 무료 플랜 크론이 하루 1회 제한이라 지금은 불가능. 유료 전환 시 재검토

### 스코프
1. `venue_business_hours` — 매장당 요일(0~6) 7행: 정기휴무/24시간/시작·종료 시간/라스트 오더
2. `rooms.closed_reason` — `'operator'` / `'auto_schedule'` 구분
3. `close_scheduled_business_sessions()` — 요일별 마감시간(자정 넘어가는 영업/24시간 영업 포함 계산) + 1시간이 지난 `active` BUSINESS 방을 자동 마감하는 함수
4. 기존 `cleanup-rooms` 크론(하루 1회)에 위 함수 호출 추가, 실행 시각을 새벽 5시로 조정
5. `GET/PUT /api/venues/[id]/business-hours` — 요일별 설정 조회/저장 (라스트 오더 유효성 검사 포함)
6. `POST /api/venues/[id]/session`(영업 시작)에 "영업시간 7일 전부 설정됐는지" + "오늘이 정기휴무가 아닌지" 검증 추가
7. 운영자 설정 화면에 요일별 영업시간 편집 화면(전체 동일 적용 토글, 24시간/휴무 시 입력 비활성화) 추가

### 확정
- 영업일 귀속은 방 생성 시각(`created_at`) 기준 — §2.1 "영업일 귀속 기준"
- 자동 마감 판정 기준은 오직 운영자가 선언한 영업시간뿐 — 참여자 활동량 추론 안 씀
- 자동 마감(`auto_schedule`)이어도 그 시간의 실제 상호작용 데이터는 대시보드 집계에서 제외하지 않음 — 데이터 자체는 신뢰할 수 있기 때문
- 크론은 하루 1회(새벽 5시), 최대 24시간 지연 가능 — Vercel 무료 플랜 제약, 유료 전환 시 매시간으로 좁힐 예정
- 요일별 영업시간 전부 설정해야만 "오늘 영업 시작" 가능

### 미확정
- 요일별이 아니라 특정 날짜(공휴일 등) 단위의 임시 휴무/시간 변경 — 지금은 지원하지 않음, 필요해지면 별도 확장
- Discovery 도메인(§2.7)에 "영업 중"/"영업 시간 안내" 배지를 노출하는 것 — 이번 스코프에는 포함하지 않음(요청 시 별도 진행)

## Phase 6 상세 — Staff 도메인 (직원 교대 + 친절도 투표) + operation_events 메모

### 스코프
1. `staff_members` — 매장별 직원 명부(이름), 운영자 설정 화면에서 추가/삭제(소프트 삭제, `is_active`)
2. `staff_shifts` — 방 화면에서 운영자가 직원을 골라 출근/퇴근 처리, `room_id`에 직접 귀속, 삭제되지 않는 감사 이력
3. `staff_evaluations` — 참여자 나가기 흐름에 "가장 친절했던 직원 1명 선택"(스킵 가능) 추가, `UNIQUE(room_id, participant_id)`. 후보 목록은 그 Room에 `staff_shifts` 기록이 있는 직원으로 한정
4. `operation_events` — 방 화면에서 운영자가 남기는 자유 텍스트 타임스탬프 메모. 방 화면에 실시간 목록으로 노출되고, 마감 후에는 대시보드 TrendLine 위에 그 시각 마커로 표시되어 호버/터치 시 내용을 보여줌
5. 대시보드 API(`get_operator_dashboard()` 또는 별도 조회)에 일자별 메모 목록을 포함해, TrendLine이 마커를 그릴 수 있게 함

### 확정 (사용자 결정 사항)
- `operation_events`는 사전 정의된 이벤트 타입 목록이 아니라 자유 텍스트 메모다 (문서 초안의 "게임 시작/음악 변경" 등은 예시일 뿐, 고정 enum 아님)
- 교대 출근/퇴근은 방 화면(실시간)에서 처리 — 별도 직원 관리 화면이 아님 (직원 명부 자체의 추가/삭제만 설정 화면에서)
- 친절도 투표는 별점이 아니라 "가장 친절한 직원 1명 선택" — 집계는 득표수
- 메모/교대 정보는 방 화면 실시간 + 마감 후 대시보드 두 군데 모두에 노출
- 운영 리포트(대시보드) UI 자체의 필터/분석 방식 개선은 이번 스코프 밖 — 추후 피그마 리디자인과 함께 별도 진행

### 미확정
- 메모에 사진/첨부파일 등 텍스트 외 형식을 지원할지 — 지금은 텍스트만
- 친절도 투표 결과를 참여자에게도 공개할지(예: "오늘의 친절왕") 아니면 운영자 전용 집계로만 둘지 — 지금은 운영자 대시보드 집계만 가정, 필요해지면 확인 후 진행

### 구현 완료 요약
- `supabase/migrations/0011_staff_and_events.sql`, `0012_operation_events_dashboard.sql`
- 직원 명부: `/operator/settings/[id]/staff` 페이지 + `/api/venues/[id]/staff`
- 교대 출근/퇴근: 방 화면(운영자 전용) + `/api/rooms/[code]/staff-shifts`
- 친절도 투표: 참여자 나가기 시 `KindnessVoteModal` + `/api/rooms/[code]/staff-evaluations` (PERSONAL 방·후보 없는 매장은 기존 confirm+즉시 나가기 그대로 유지)
- 운영 메모: 방 화면(운영자 전용) + `/api/rooms/[code]/events`, `get_operator_dashboard()`의 `daily[].events`를 `TrendLine`이 호버/탭 마커로 표시

## Phase 8.5 상세 — B2B 전용 플랫폼 전환

### 배경
사용자가 이 앱을 순수 B2B 플랫폼으로 만들고 싶다고 결정 — 개인 모임(PERSONAL) 방을 만들거나 코드로 직접 입장하는 기능을 전부 제거하고, 개인은 오직 매장 QR을 스캔해 참여자로만 들어올 수 있게 한다. PERSONAL용 코드는 별도 GitHub 저장소에 데모용으로 이미 남아있어서, 이 저장소에서는 완전히 뺄 수 있다고 판단함.

### 제거 대상 조사 결과
- `POST /api/rooms`(PERSONAL 방 생성)는 이미 사실상 죽은 코드였다 — BUSINESS 방은 전부 `POST /api/venues/[id]/session`(영업 시작)으로 만들어져서, 이 라우트 안의 BUSINESS 분기는 호출되지 않고 있었다.
- `POST /api/rooms/[code]/join`(코드 직접 입장)도 BUSINESS 방은 애초에 이 경로를 거부하도록 만들어져 있어 PERSONAL 전용이었다.
- 대부분의 화면 로직(`useRoom.ts`, 방 화면들)이 이미 `room_type` 직접 비교가 아니라 `state.venue` 존재 여부로 분기하고 있어서, 실질적인 재작성 없이 자연스럽게 "항상 BUSINESS"로 수렴하는 구조였다.

### 확정
- 삭제: `POST /api/rooms` + 테스트, `POST /api/rooms/[code]/join` + 테스트, `/join` 화면
- 재설계: `/create`(매장 등록 전용으로), 홈 화면 하단 버튼(입장하기/방 만들기 제거 → "사장님이신가요? 매장 관리"로 교체)
- `GET/PATCH /api/rooms/[code]`의 PERSONAL 분기(`else` 브랜치) 제거 — venue_id 유무만으로 판단하도록 단순화
- `RoomType` 타입을 `'PERSONAL' | 'BUSINESS'` → `'BUSINESS'` 단일값으로 좁힘 (컴파일 타임에 PERSONAL 관련 코드가 남아있으면 바로 드러나게)
- 스키마는 그대로 둠 — `rooms.room_type`/`rooms.host_session` 컬럼 삭제는 하지 않는다. `host_session`은 "이 세션을 연 운영자 계정 id"를 남기는 이력값으로 이미 재활용되고 있어 여전히 쓸모가 있고, 컬럼 삭제는 리스크 대비 얻는 게 없다.
- `delete_old_rooms()` RPC(PERSONAL 방 정리)는 그대로 둔다 — 이제 항상 매치되는 행이 없는 no-op이지만, 제거해도 얻는 게 없다.

### 미확정 / 이번에 안 건드린 것
- End Vote 도메인(`end_votes`, 참여자 다수결 방 종료) — 코드 조사 결과 참여자가 실제로 투표를 던지는 UI가 어디에도 연결되어 있지 않았다(API/타입만 존재). PERSONAL 제거와 별개로 이미 죽은 기능일 가능성이 있어 보이지만, 이번 스코프 밖이라 손대지 않았다. 나중에 확인 필요.
- `BUSINESS_RULES.md` Part 1(기존 B2C 규칙 — Room/Participant/Reaction/Atmosphere Index/Mutual Match/Chat/End Vote)은 삭제하지 않았다 — 그 문서가 설명하는 하트/HOT/채팅/쌍방매칭 메커니즘은 지금도 BUSINESS 방에서 그대로 쓰이는 살아있는 기능이기 때문이다. §1.1(Room 도메인)의 방 생성/입장 관련 행만 삭제된 코드를 반영해 갱신했다.

### 개발 공수 / 위험도 (사전 분석, 실제 진행 후 대체로 부합)
- 공수: 라우트 삭제 30분, 홈/create 재설계 반나절, 테스트 트림 반나절, 문서 정리 1~2시간, 전체 검증 1~2시간 — 총 1~2일 분량
- 위험도: 전반적으로 낮음. 핵심 상호작용 로직(하트/HOT/채팅/좌석/직원/대시보드)은 전혀 건드리지 않았고, 삭제한 라우트 2개는 이미 죽은 코드에 가까웠다.

## Phase 9 상세 — 방 화면 리디자인 (구현 완료, 사후 기록)

### 배경
사용자가 방 화면(QR 입장 후 화면) 스크린샷 5장을 전달하며 재설계 요청. 홈 지도 화면 때와 마찬가지로 처음엔 "나머지 24개 화면 = 순수 리스킨" 범주로 예상했으나, 실제로는 신규 기능이 다수 포함되어 있었다 — 홈 지도 화면(위 섹션 300번째 줄 "정정")과 동일한 패턴이 반복됨.

### 스코프 (구현 완료)
| # | 항목 | 비고 |
|---|---|---|
| 1 | 하단 4탭 재구성 (매장/별점/채팅/직원, 인스타그램 스타일) | 기존 화면들을 탭으로 재배치 |
| 2 | 좌석 선택 방식 변경 | 최초엔 "방 화면에 통합"으로 구현했다가, 이후 사용자가 "QR 입장 → 전용 좌석 선택 화면(신규) → 좌석 선택 완료 시 방 입장 처리"로 재확정(`BUSINESS_RULES.md` §2.8). **이 재확정 시점 기준으로 코드가 아직 반영 전** — 현재 코드는 좌석 미선택 상태로도 방 화면에 먼저 진입하는 이전 버전이다 |
| 3 | 외부 QnA 채널 신설 (`venue_qna`) | Chat 도메인과 분리된 신규 테이블. 매장에 입장하지 않은 외부인도 작성 가능, 외부인만 60초 쿨타임. 상세: `BUSINESS_RULES.md` §2.15 |
| 4 | 좌석 배치 에디터 (`venue_layout_items`) | 좌석 외에 테이블/구역(box)/출입문/안내 텍스트를 운영자가 자유 배치. 상세: `BUSINESS_RULES.md` §2.8 |
| 5 | 매장 소개(`venues.description`) | 방 화면 하단에 노출되는 매장 한 줄 소개. 운영자 설정에서 자유롭게 수정 가능(매장명과 달리 변경 제약 없음). 상세: `BUSINESS_RULES.md` §2.2 |
| 6 | 개발자 테스트 페이지 (`/dev/rooms`) | 카메라/GPS 없이 QR 입장을 재현하는 운영자 전용 테스트 도구. Business Rule이 아니라 순수 개발 도구라 `BUSINESS_RULES.md`엔 기록하지 않음 |

### 확정
- **리스킨이 아니라 신규 기능 다수 포함이었음** — 홈 지도 때와 같은 사유로 "나머지 24개 화면"에서 이 화면은 제외하고 별도 스코프로 취급한다
- HOT 지수 계산 로직(`hotIndex.ts`)에 있던 레이스 컨디션(폴링이 realtime 갱신을 되돌리는 버그)도 이 작업 중 함께 발견·수정됨(문서 규칙 변경은 없음, 순수 버그 픽스)

### 미확정 / 후속 작업 필요
- 위 표 2번(좌석 선택 전용 화면 + 방입장 게이트)은 **문서만 재확정된 상태고 코드는 아직 이전 버전** — 다음 구현 작업 대상
- 지도 매장 화면 미리보기(§2.7 신규, 방 화면 "매장" 탭 재사용한 관찰자 뷰)도 문서만 확정, 코드 미착수

## Phase 9.5 상세 — Subscription 도메인 (구독/결제) 신설

### 배경
Phase 9 리뷰 중 사용자가 확정: "구독 안 한(우리 기능들이 작동되지 않는) 매장은 빨간 LIview 표시가 없다" — 이건 단순 배지 표시 여부가 아니라 **미구독 매장은 HOT/만족도/채팅/좌석 기능 자체가 동작하지 않는다**는 뜻이라, Phase 9의 UI 변경 범위를 넘어서는 새 도메인이다. 상세 규칙은 `BUSINESS_RULES.md` §0.1/§2.14 참고.

### 스코프
1. `venues.subscription_status`(또는 별도 `subscriptions` 테이블) — 스키마는 PG 선정 후 확정
2. PG(결제대행사) 연동 — 정기결제(구독형 과금) 지원 여부가 선정 기준
3. reactions/live-chat/seats API에 구독 확인 게이트 추가 (분산 vs 중앙화 방식은 착수 시점에 결정)
4. Discovery 화면의 구독 배지 노출 (`BUSINESS_RULES.md` §2.7 "구독 배지" 규칙)

### 확정
- 구독 만료돼도 기존 Reaction/Chat/좌석 데이터는 삭제·은닉하지 않는다 — 게이트는 신규 쓰기 동작에만 적용
- 미구독 매장도 지도에서 완전히 숨기지 않는다 — 위치/영업시간만 노출, 배지·실시간 기능만 비활성

### 리스크 — 왜 별도 Phase로 뗐는가
- **개발 공수보다 리드타임이 문제**: PG사 계약/심사(사업자 서류, 정산 계좌 인증)는 개발과 무관하게 며칠~몇 주가 걸릴 수 있다 — **개발 착수와 별개로 지금 바로 PG사 컨택을 시작하는 걸 권장**
- 결제 자체(웹훅/정산/보안)가 이번 로드맵 전체에서 가장 신중해야 하는 부분

### 임시 운영 방안 (확정)
결제 연동 전까지는 `subscription_status`를 시스템 관리자가 수동으로 세팅해, Phase 9의 나머지 항목(1~6번)을 결제 없이 먼저 검증한다. PG 연동이 끝나면 수동 세팅을 웹훅 기반 자동 갱신으로 교체.

### 미확정
- PG사 선정, 실제 스키마, 게이트 구현 위치(분산 vs 중앙화) — 전부 착수 시점에 결정
