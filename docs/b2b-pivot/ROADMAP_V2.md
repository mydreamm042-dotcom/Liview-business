# MySTAR/Liview B2B 로드맵 v2

## 이 문서의 위치
기존 `B2B_PIVOT_DESIGN.md`(섹션 7)와 `IMPLEMENTATION_CHECKLIST.md`가 Phase 순서를 정의했지만, 새 아이디어(지도 기반 홈 화면, 좌석 배치)가 그 순서에 영향을 주므로 **이 문서가 Phase 순서에 대해 최신 기준**이다. 세부 태스크 체크리스트는 기존 `IMPLEMENTATION_CHECKLIST.md`를 계속 참고하되, 몇 번째로 하느냐는 이 문서를 따른다.

이 문서는 계속 갱신된다 (v2 안에서 개정). 새 아이디어가 들어올 때마다 새 파일을 또 만들지 않고, 이 문서 하나를 최신 상태로 유지한다 (`CHANGE_INTAKE_PROCESS.md` 원칙).

---

## 지금까지 반영된 새 아이디어

### ① 지도 기반 홈 화면 + 실시간 핫플레이스 탐색
> "Liview 기본 화면 = 지도. 하단 UI: 입장하기 / 실시간 핫한 가게 찾기 / 방만들기. 방 코드는 제공하지 않는다 (원격 참여 악용 방지)."

새 도메인이 아니라, 이미 설계해둔 **Discovery 도메인**의 역할이 커진 것이다 (부가 기능 → 앱의 기본 진입점). 핵심 신규 규칙: **Discovery 화면은 방 코드/QR을 절대 노출하지 않는다** (`BUSINESS_RULES.md` §2.6).

### ② 좌석 배치도(자리배치) + 좌석별 실시간 HOT 표시
> "가게 입장 시 사장님이 만들어둔 자리배치도로 이동해 좌석을 선택. 좌석마다 HOT을 탭하고 있는지 표시됨. 사장님용 관리자 기능(좌석 클릭 시 경고/서비스/쿠폰/강제 좌석이동)도 필요한데 아직 설명 안 함."

새로운 **Seating 도메인**을 도입했다 (`BUSINESS_RULES.md` §2.7). 단, **참여자 쪽(좌석 선택 + 좌석별 HOT 표시)만 스펙이 확정**됐고, **운영자 관리자 기능은 아직 설명을 못 들어서 규칙을 만들지 않았다** — 설명을 받으면 이 문서와 BUSINESS_RULES.md를 다시 갱신한다.

## 재정렬된 Phase 순서

| Phase | 내용 | 상태 |
|-------|------|------|
| **1** | Foundation — venues 테이블, room_type, closed 상태 | ✅ 완료 (main 병합) |
| **2** | Room Configuration — 매장 브랜딩, 운영자 설정 화면 | ✅ 완료 (main 병합) |
| **3** | Liview 홈 — 지도 진입점 + 실시간 탐색 (Discovery + Public Transparency MVP) | 다음 작업 |
| **4 (신규)** | 좌석 배치 & 좌석 선택 (Seating MVP — 참여자 쪽만) | 스펙 일부 대기 |
| 5 (기존 3에서 밀림) | 운영자 대시보드 | 대기 |
| 6 (기존 4 + Staff 추가안) | 이벤트 타임라인 + 직원 교대/친절도 평가 | 대기 |
| 7 (기존 5 + Review 추가안) | 리뷰 유도 + 검증 리뷰(venue_reviews) | 대기 |
| 8 (기존 6) | Polish & Integration | 대기 |
| **미배정** | 좌석 관리자 기능(경고/서비스/쿠폰/좌석이동) — 스펙 받으면 Phase 번호 배정 | 스펙 대기 |

**바뀐 것은 순서뿐, 내용은 그대로다.** 이미 끝난 Phase 1/2는 건드리지 않는다. 기존 Phase 3(운영자 대시보드)은 사라진 게 아니라 Phase 5로 밀렸을 뿐이다.

## Phase 3 상세 — Liview 홈 (지도 + 실시간 탐색)

### 왜 이걸 다음으로 당겼나
- 사용자가 "앱의 기본 화면"이라고 못박았다 → 다른 어떤 기능보다 먼저 마주치는 화면.
- 필요한 하부 데이터(Venue의 위치/카테고리, HOT 지수, 만족도)는 이미 Phase 1에서 준비되어 있다.

### 스코프
1. `get_live_hot_venues()` 함수 실제 마이그레이션 반영 (현재 `B2B_MIGRATION_V2.sql`엔 설계만 있고 `supabase/migrations/`엔 미적용)
2. `GET /api/discover/venues` — 위치 기반 실시간 HOT 매장 목록 (카테고리 필터, 정렬)
3. 홈 화면 교체 — `src/app/page.tsx`를 지도 기반으로. 하단 3버튼: 입장하기 / 실시간 핫한 가게 찾기 / 방 만들기
4. 매장 카드/상세 화면 — 실시간 HOT·만족도, opt-in 매장만 채팅 프리뷰. **방 코드/QR 절대 미표시**
5. 공개 채팅 최소 기능 — `venues.public_chat_enabled` 토글 + 읽기 전용 API

### 미확정
- 지도 SDK (카카오맵/네이버지도/구글맵) — 보류 중
- Discovery 홈을 PERSONAL 참여자에게도 그대로 보여줄지

## Phase 4 상세 — 좌석 배치 & 좌석 선택 (Seating MVP)

### 왜 Phase 3 바로 다음인가
- 참여자 흐름상 "지도에서 매장 발견 → 실제 방문 → QR 입장 → **좌석 선택**"으로 자연스럽게 이어지는 다음 단계다.
- Venue/Room/Participant 도메인이 이미 있어 추가 스키마가 크지 않다 (신규 테이블 `venue_seat_layouts` + `participants.seat_id` 정도).
- 운영자 좌석 관리자 기능(경고/서비스/쿠폰/좌석이동)은 스펙이 없으므로 **이 Phase에는 포함하지 않는다.** 설명을 들으면 별도 Phase로 분리해서 로드맵에 추가한다.

### 스코프 (확정된 부분만)
1. `venue_seat_layouts`(가칭) 테이블 — 매장 좌석 배치 데이터, 운영자가 구성
2. 운영자 좌석 배치 편집기 — Phase 2 브랜딩 편집기와 같은 패턴 재사용
3. `participants.seat_id` — 참여자가 BUSINESS 방 입장 시 선택한 좌석
4. 참여자용 자리배치도 화면 — 좌석 선택 UI, 좌석별 실시간 HOT 표시(파생 계산, `reactions`를 `seat_id`로 조인)

### 미확정 — 스펙 대기
- **좌석 선택이 필수인지 스킵 가능한지**
- **운영자 관리자 기능 전체** (좌석 클릭 시 경고 메시지/서비스/쿠폰 제공/관리자 권한 강제 좌석 이동) — 설명 필요. 이건 Operator Analytics 도메인의 확장일 수도 있고, 완전히 새로운 "Service Operations" 도메인이 필요할 수도 있어, 설명을 들은 후 도메인 매핑부터 다시 한다.

### 영향받지 않는 것
- PERSONAL 방에는 좌석 개념 자체가 없다 (Venue가 없으므로)
- 기존 QR 입장 흐름은 그대로, 입장 "다음" 단계로 좌석 선택이 추가될 뿐
