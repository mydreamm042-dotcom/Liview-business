# MySTAR Business Rule 문서

## 목적
이 문서는 (1) 시스템을 구성하는 **도메인을 먼저 정의**하고, (2) 각 도메인이 소유한 Business Rule을 코드 근거와 함께 정리하여, "기존 Business Rule은 최대한 유지한다"는 개발 원칙의 기준선(baseline)을 명확히 한다. 모든 기존 규칙 항목에는 소스 근거 파일 경로를 표기했다.

규칙은 테이블이나 화면 단위가 아니라 **도메인 단위**로 조직한다. 도메인이란 "하나의 핵심 개념을 중심으로, 그 개념의 생성·상태 전이·불변식(invariant)을 스스로 책임지는 경계"를 말한다. 예를 들어 HOT 지수는 `reactions` 테이블의 일부(type='hot')지만, 감쇠·증가율 계산이라는 독자적인 규칙을 가지므로 별도 도메인으로 분리한다.

## Part 0. 도메인 정의 (Domain Definitions)

### 0.1 도메인 총괄표

| 도메인 | 정의 | 핵심 엔티티(테이블) | 의존 도메인 |
|--------|------|---------------------|--------------|
| **Room** (방) | 참여자들이 모이는 세션 하나의 생성·상태·생명주기를 책임지는 도메인 | `rooms` | Venue(선택적) |
| **Participant** (참여자) | 특정 방에 대한 한 사람의 참여 정체성(입장/나가기/재입장)을 책임지는 도메인. BUSINESS 방에서는 위치 기반 반경 제한(입장 시 + 입장 후 지속)도 이 도메인이 책임진다 | `participants` | Room, Venue(BUSINESS 위치 제한 시) |
| **Reaction** (리액션) | 하트/자제시그널/별점/HOT탭이라는 4종 상호작용의 생성 규칙과 쿨타임을 책임지는 도메인 | `reactions` | Room, Participant |
| **Atmosphere Index** (분위기 지수/HOT) | Reaction 중 `hot` 타입 데이터로부터 "지금 이 순간의 분위기 수치(0~100)"를 계산해내는 파생 도메인 | (reactions 기반 계산, 별도 테이블 없음) | Reaction |
| **Mutual Match** (쌍방 매칭) | Reaction 중 `heart` 타입 데이터로부터 "서로 호감이 오갔는가"를 판정하는 파생 도메인 | (reactions 기반 계산, 별도 테이블 없음) | Reaction |
| **Chat** (채팅) | 방 내부의 공용 메시지 기록을 책임지는 도메인 | `messages` | Room, Participant |
| **End Vote** (종료 투표) | 참여자들이 방 종료를 합의하는 투표를 책임지는 도메인 | `end_votes` | Room, Participant |
| **Venue** (매장) 🆕 | 하나의 물리적 매장이 시간에 걸쳐 여러 방(세션)을 만들어도 유지되는 브랜딩·위치·설정을 책임지는 도메인 | `venues`, `venue_business_hours`(요일별 영업시간, Phase 5.5) | Operator(소유자), (최상위, 다른 도메인이 참조) |
| **Staff** (직원) 🆕 | 매장 소속 직원의 목록, 교대 근무, 참여자로부터 받는 친절도 평가를 책임지는 도메인 | `staff_members`, `staff_shifts`, `staff_evaluations` | Venue, Room, Participant |
| **Review** (검증 리뷰) 🆕 | 참여자의 실제 세션 데이터를 근거로 한 "조작 불가능한 방문 인증 리뷰"의 생성·공개여부를 책임지는 도메인 | `venue_reviews` | Venue, Room, Participant, Reaction |
| **Public Transparency** (공개 채팅) 🆕 | 매장이 opt-in한 경우에 한해, 방 채팅을 비참여자에게도 노출하는 규칙을 책임지는 도메인 | (Chat 도메인 데이터를 조건부로 재노출, 별도 테이블 없음) | Chat, Venue |
| **Discovery** (탐색/주변추천) 🆕 | 참여자의 현재 위치를 기준으로, 실시간으로 분위기가 좋은 주변 매장을 찾아주는 도메인 | (Venue + Room + Reaction 기반 계산, 별도 테이블 없음) | Venue, Room, Reaction |
| **Seating** (좌석/자리배치) 🆕 | 매장 내부의 물리적 좌석 배치를 운영자가 구성하고, 참여자가 입장 시 좌석을 선택하며, 운영자가 참여자의 좌석을 직접 옮길 수 있고(드래그/모바일 롱프레스), 좌석 단위로 실시간 HOT 활동과 착석 경과시간을 보여주는 도메인 | `venue_seats`(`position_x`/`position_y` 자유 배치 좌표 포함, 구현 완료), `participants.seat_id`+`seat_assigned_at`(구현 완료) | Venue, Room, Participant, Reaction |
| **Guest Care** (손님 케어) 🆕 | 운영자가 자리배치도에서 특정 손님을 지목(우클릭/터치)해 개입하는 행위를 책임지는 확장형 도메인. Reaction 도메인의 `warning`(참여자 간 익명 자제 시그널)과는 별개 개념 — 혼동 방지를 위해 "운영자 경고 메시지(Operator Alert)"로 구분 명명. 쿠폰 지급은 사양 미확정으로 Phase 4 범위 밖(별도 Phase로 연기) | `operator_alerts`(구현 완료), `venue_coupons`+`coupon_grants`(추후 별도 Phase에서 신설 예정) | Venue, Room, Participant, Seating |
| **Operator Analytics** (운영 분석) 🆕 | 위 모든 도메인의 데이터를 읽기 전용으로 재가공해 대시보드/퍼널/리포트/이벤트 타임라인을 제공하는 도메인 (자체 상태를 쓰지 않음) | `get_operator_dashboard()`(구현 완료, Phase 5) + `operation_events`(기록용, Phase 6 예정) | 전 도메인 |
| **Operator** (운영자 계정) 🆕 | 매장 운영자(사람)의 회원가입/로그인/신원을 책임지는 도메인. Venue 도메인은 "매장"을, Operator 도메인은 "그 매장을 가진 사람"을 책임진다 — 종전엔 이 둘이 `operator_owner_token`(브라우저별 임의 토큰)이라는 하나의 값으로 뭉뚱그려져 있었으나, 정식 회원 개념 도입으로 분리한다 | `operators` (Supabase Auth `auth.users`와 1:1), `venues.owner_id` | Venue |

### 0.2 도메인 관계도

```
Operator (운영자 계정) ──1:N(소유)── Venue (매장) ──1:N── Room (방) ──1:N── Participant (참여자)
                                        │                    │                    │
                                        │                    │                    ├──1:N── Reaction (하트/경고/별점/HOT)
                                        │                    │                    │            │
                                        │                    │                    │            ├─ 파생 ─> Atmosphere Index (HOT 지수)
                                        │                    │                    │            └─ 파생 ─> Mutual Match (쌍방 매칭)
                                        │                    │                    │
                                        │                    │                    ├──1:N── Chat (메시지)
                                        │                    │                    │            └─ 조건부 재노출 ─> Public Transparency
                                        │                    │                    │
                                        │                    │                    ├──1:N── End Vote (종료 투표)
                                        │                    │                    │
                                        │                    │                    └──1:1(선택)── seat_id ──ref──> Venue Seat Layout (좌석)
                                        │                    │                                                        ├─ 파생 ─> 좌석별 HOT 표시 (Reaction 조인)
                                        │                    │                                                        ├─ 파생 ─> 착석 경과시간 (seat_assigned_at 기준)
                                        │                    │                                                        └─ 운영자 조작 ─> 좌석 이동(드래그/롱프레스, 참여자 화면에도 반영)
                                        │                    │
                                        │                    ├──1:N── Venue Review (Room+Participant 스냅샷 기반)
                                        │                    ├──1:N── Staff Shift (그 영업일 근무자, room_id 직접 귀속)
                                        │                    ├──1:N── Operation Event (운영자 타임스탬프 메모, Phase 6)
                                        │                    └──ref(seat_id 경유)── Guest Care (Operator Alert / Coupon Grant)
                                        │
                                        ├──1:N── Venue Business Hours (요일별 영업시간)
                                        │            └─ 근거 ─> Room의 마감시간 기반 자동 마감 (closed_reason='auto_schedule')
                                        ├──1:N── Staff Member ──1:N── Staff Evaluation (Participant 투표, Room에 귀속)
                                        ├──1:N── Venue Seat Layout (매장이 소유하는 좌석 배치도)
                                        ├──1:N── Venue Coupon (매장이 앱에 등록한 쿠폰 카탈로그) ──1:N── Coupon Grant (특정 참여자에게 지급)
                                        │
                                        └──조회 대상──> Discovery (위치 기반 실시간 랭킹)

Operator Analytics: 위 전체 도메인을 읽기 전용으로 가로질러 재가공 (자체 쓰기 없음, operation_events 제외)
```

### 0.3 도메인 경계 원칙

- **Room ≠ Venue**: Room은 "한 번의 세션"이고 Venue는 "그 세션들을 만드는 주체(매장)"이다. PERSONAL 방은 Venue에 속하지 않는다(venue_id가 없음).
- **Reaction은 원본, Atmosphere Index/Mutual Match는 파생**: 원본 리액션 데이터는 절대 수정되지 않으며, HOT 지수와 쌍방 매칭은 매번 원본으로부터 재계산되는 읽기 전용 파생값이다. 파생 도메인은 자신만의 저장 상태를 갖지 않는다.
- **Chat과 Public Transparency는 같은 데이터, 다른 노출 규칙**: 별도 테이블을 만들지 않고, 동일한 `messages` 데이터에 대해 "누구에게 보여줄 것인가"라는 노출 규칙만 다르게 적용한다.
- **Review는 Reaction의 스냅샷이지 새로운 입력이 아니다**: Review 도메인은 참여자가 직접 작성하는 자유 입력을 받지 않는다. 오직 Reaction/Room 도메인에 이미 존재하는 값을 특정 시점에 복사(snapshot)해서 저장할 뿐이다.
- **Operator Analytics는 상태를 소유하지 않는다**: 이 도메인은 다른 모든 도메인의 데이터를 읽어 집계할 뿐, `operation_events`(운영자가 직접 기록하는 이벤트 로그)를 제외하면 자체 쓰기 규칙이 없다.
- **좌석별 HOT도 파생값이지 새 원본이 아니다**: 좌석에 "지금 핫을 탭하는 중"이라고 표시하는 것은 `reactions`(hot 타입)를 참여자의 `seat_id`로 조인해 계산하는 파생값일 뿐, 좌석마다 별도의 HOT 원본 데이터를 새로 만들지 않는다 — Atmosphere Index 도메인과 동일한 원칙.
- **Seating ≠ Guest Care**: Seating은 "누가 어디 앉아 있는가"(위치)를 책임지고, Guest Care는 "그 손님에게 운영자가 무엇을 하는가"(개입)를 책임진다. 둘 다 같은 화면(자리배치도)에서 트리거되지만 서로 다른 도메인이다 — Guest Care는 앞으로 계속 액션 종류가 늘어날 확장형 도메인이라 Seating과 분리해뒀다.
- **"경고" 용어 충돌 주의**: Reaction 도메인의 `warning`(자제 시그널, 참여자↔참여자 익명 신호)과 Guest Care의 "운영자 경고 메시지"(운영자→특정 참여자, 자유 텍스트, 발신자 실명)는 완전히 다른 개념이다. 구현 시 반드시 별개 이름(`operator_alerts` 등)을 쓰고 `reactions.type='warning'`과 절대 혼용하지 않는다.
- **Guest Care는 아직 일부만 확정됐다**: 경고 메시지(자유 텍스트)와 쿠폰 지급(매장 등록 카탈로그 중 선택)까지는 확정됐지만, 그 외 세부사항(메시지 전달 방식, 쿠폰 등록 플로우, 손님의 쿠폰 수령 확인 방법)은 아직 설명이 없어 규칙을 추측해서 만들지 않는다. 사용자가 "앞으로 기능이 더 늘어날 가능성이 높다"고 명시했으므로, 액션 종류를 쉽게 추가할 수 있는 구조로 설계한다.
- **Operator ≠ Venue**: Operator는 "그 매장을 가진 사람(로그인 계정)"을 책임지고, Venue는 "매장 자체(브랜딩·설정·영업시간)"를 책임진다. 소유 관계는 `venues.owner_id` 외래키 하나로 표현되며(1 운영자 : N 매장), 매장의 자동 마감·대시보드 조회 권한 등은 전부 이 소유 관계를 근거로 판정한다.

## Part 1. 도메인별 Business Rule — 기존 B2C (변경 금지, 그대로 유지)

### 1.1 Room 도메인

**정의**: 참여자들이 모이는 세션 하나의 생성·상태·생명주기를 책임진다.

| 규칙 | 내용 | 근거 |
|------|------|------|
| 방 코드 형식 | 영문 대문자+숫자 6자리, 중복 시 최대 10회 재시도 후 생성 | `src/lib/session.ts` (generateRoomCode), `src/app/api/rooms/route.ts` |
| 방 생성자 = 호스트 | 방 생성 시 자동으로 닉네임 "호스트"인 참여자 1명이 함께 생성됨 (Participant 도메인과의 경계: Room 생성이 Participant 생성을 트리거) | `src/app/api/rooms/route.ts` |
| host_session 비공개 | 방 생성/조회 응답에서 `host_session`은 항상 제거 후 반환 (devtools로 탈취해 타인이 호스트 행세하는 것을 방지) | `src/app/api/rooms/route.ts`, `src/app/api/rooms/[code]/join/route.ts` |
| 방 상태 | `active` → `ended` 2단계. `ended` 방은 입장 불가 | `supabase/schema.sql`, `join/route.ts` |
| 자동 정리 (Cleanup) | `ended` 상태로 24시간 경과 시 삭제 / `active` 상태로 2일 경과 시(방치된 방) 삭제. Vercel Cron이 주기 호출 | `supabase/schema.sql` (delete_old_rooms), `src/app/api/cron/cleanup-rooms/route.ts` |
| 연쇄 삭제 | 방 삭제 시 Participant/Reaction/End Vote/Chat 도메인 데이터가 모두 `ON DELETE CASCADE`로 함께 삭제 (Room이 하위 도메인의 생명주기를 소유) | `supabase/schema.sql` |

### 1.2 Participant 도메인

**정의**: 특정 방에 대한 한 사람의 참여 정체성(입장/나가기/재입장)을 책임진다.

| 규칙 | 내용 | 근거 |
|------|------|------|
| 참여자 유니크 제약 | (room_id, session_token) 유니크 — 동시 이중 입장 요청 레이스를 DB 레벨에서 방지 | `supabase/schema.sql` 주석, `join/route.ts` |
| 나가기 = Soft Leave | 참여자 "나가기"는 행 삭제가 아니라 `left_at` 타임스탬프만 기록. 삭제 시 Reaction/Chat/End Vote 도메인에 남은 이 참여자 관련 데이터가 연쇄 삭제되어 재입장 시 초기화되는 것을 방지 | `src/app/api/participants/route.ts` (DELETE) |
| 재입장 = 동일 인물 복귀 | 같은 세션 토큰으로 재입장 시 새 참여자를 만들지 않고 기존 행의 `left_at`을 비우고 닉네임만 갱신 → 받은 하트, 매칭 이력, HOT 기여분이 그대로 유지됨 | `join/route.ts` |
| 입장 레이스 처리 | 동시 입장 요청으로 유니크 제약(23505) 충돌 시, 실패 처리하지 않고 먼저 생성된 참여자를 그대로 반환 | `join/route.ts` |
| 참여도 이벤트 1회 기록 | `result_viewed_at`, `chat_opened_at`은 최초 1회만 기록하고 이후 갱신하지 않음 (몇 번 열었는지가 아니라 "열어봤는지/언제 처음"만 필요) | `src/app/api/participants/route.ts` (PATCH) |

### 1.3 Reaction 도메인

**정의**: 하트/자제시그널/별점/HOT탭 4종 상호작용의 생성 규칙과 쿨타임을 책임진다. Atmosphere Index와 Mutual Match 도메인은 이 도메인의 데이터를 읽기만 하며 직접 쓰지 않는다.

| 규칙 | 내용 | 근거 |
|------|------|------|
| 리액션 타입 | `heart`(하트) / `warning`(자제 시그널) / `star`(별점) / `hot`(HOT 탭) 4종 고정 | `supabase/schema.sql` CHECK 제약 |
| 자기 자신 제외 | `heart`, `warning` 타입은 수신자가 발신자 본인이면 거부 (`star`, `hot`은 대상이 없거나 방 전체 대상이라 예외) | `src/app/api/reactions/route.ts` |
| 별점 범위 | `star` 타입의 value는 1~5 사이만 허용 | `src/app/api/reactions/route.ts` |
| 자제 시그널(warning) 쿨타임 | 5분 (300,000ms) | `src/lib/cooldown.ts` (WARNING_COOLDOWN_MS) |
| 별점(star) 쿨타임 | 30분 (1,800,000ms) | `src/lib/cooldown.ts` (STAR_COOLDOWN_MS) |
| 쿨타임 원자적 처리 | 쿨타임 확인과 저장을 `pg_advisory_xact_lock` 기반 DB 함수(`submit_cooldown_reaction`) 안에서 하나의 트랜잭션으로 처리 — "확인 후 저장" 사이 레이스로 쿨타임이 뚫리는 것을 방지. 잠금 키는 (발신자+리액션 타입) 조합이라 다른 발신자/다른 타입끼리는 서로 대기하지 않음 | `supabase/schema.sql` (submit_cooldown_reaction) |
| 서버 사이드 집계 | 하트/경고 카운트, 평균 만족도는 클라이언트가 원본 리액션 전체를 내려받아 계산하지 않고 DB 함수(`get_reaction_summary`)가 미리 계산해서 반환 — 폴링(3초 주기)이 참여자가 많아질수록 느려지는 것을 방지 | `supabase/schema.sql` |

### 1.4 Atmosphere Index 도메인 (HOT 지수)

**정의**: Reaction 도메인의 `hot` 타입 데이터로부터 "지금 이 순간의 분위기 수치(0~100)"를 계산하는 파생 도메인. 자체 저장 상태를 갖지 않고 매번 원본 리액션에서 재계산한다.

| 규칙 | 내용 | 근거 |
|------|------|------|
| 유지 구간 | 탭 이후 5분(HOT_HOLD_MS)간 값 그대로 유지 | `src/lib/hotIndex.ts` |
| 감쇠 구간 | 유지 구간 이후 10분(HOT_DECAY_MS)에 걸쳐 선형적으로 0까지 감소, 이후 0 고정 | `src/lib/hotIndex.ts` |
| 탭당 증가율 | 탭이 발생한 "그 순간"의 활성 참여자 수에 반비례 (`4 / sqrt(참여자수)`) — 참여자 4명일 때 정확히 2%가 되도록 보정된 기준값. 인원이 적을수록 한 탭의 임팩트가 크다 | `src/lib/hotIndex.ts` (HOT_BASE_INCREMENT) |
| 증가율 고정 시점 | 탭 순간의 참여자 수는 Reaction 도메인의 `value` 컬럼에 스냅샷으로 기록되며, 이후 참여자 수가 바뀌어도 이미 반영된 탭의 증가율은 재계산되지 않음 | `src/app/api/reactions/route.ts`, `src/lib/hotIndex.ts` |
| 최댓값 | 100 상한 (그 이상 누적되지 않음) | `src/lib/hotIndex.ts` (simulateHotTaps) |
| 계산 방식 | "평생 누적 탭 개수" 기반이 아니라 "시간순 시뮬레이션" 기반 — 오래 조용하다가 탭 1번만 눌러도 과거 히스토리 때문에 값이 튀지 않음 | `src/lib/hotIndex.ts` 주석 |
| 화면 표시 최적화 | 히스토리 전체 재계산(`simulateHotTaps`)은 탭 목록이 바뀔 때만 수행하고, 1초 단위로 갱신되는 "지금 이 순간" 표시값은 O(1) 연산(`hotIndexAt`)으로 구함 | `src/lib/hotIndex.ts` |

### 1.5 Mutual Match 도메인 (쌍방 매칭)

**정의**: Reaction 도메인의 `heart` 타입 데이터로부터 "서로 호감이 오갔는가"를 판정하는 파생 도메인.

| 규칙 | 내용 | 근거 |
|------|------|------|
| 매칭 판정 기준 | 방금 하트를 보낸 직후, "받은 쪽이 보낸 쪽 못지않게(개수 이상) 하트를 보내온 상태"면 매칭 성립 (`receiverCount > 0 && receiverCount >= senderCount`) | `src/lib/server/mutual.ts` |
| 판정 로직 단일화 | 전송 시 배너(발신자 화면)와 수신 확인 폴링(수신자 화면) 두 곳 모두 동일한 `checkMutualHeart` 함수를 공유 — 기준이 어긋나지 않도록 함 | `src/lib/server/mutual.ts` 주석 |

## Part 2. 도메인별 Business Rule — 신규 B2B (BUSINESS 방 전용)

> 아래 규칙은 모두 **BUSINESS 타입 방에서만 적용**되며, PERSONAL 방에는 어떠한 영향도 주지 않는다.

### 2.1 Room 도메인 확장 규칙 (Room Type / 마감)

| 규칙 | 내용 |
|------|------|
| 기본값 | 방 생성 시 `room_type`을 지정하지 않으면 `PERSONAL`로 간주 (하위 호환) |
| 기능 게이팅 | Venue/Staff/Review/Public Transparency/Discovery/Operator Analytics 등 모든 B2B 도메인 기능은 `room_type = 'BUSINESS'`일 때만 노출/동작 |
| 되돌리기 금지 | 방 생성 이후 `room_type`은 변경 불가 (PERSONAL ↔ BUSINESS 전환 시나리오는 지원하지 않음 — 운영 데이터 정합성을 위해) |
| 상태값 확장 | `rooms.status`에 `closed`를 추가 (`active`/`ended`/`closed`) |
| BUSINESS 방 전용 상태 | BUSINESS 방은 `active → closed`로만 전이하며, `ended` 상태를 사용하지 않는다 |
| 삭제 금지 | `closed` 상태의 BUSINESS 방은 어떤 자동 정리(cleanup) 로직에서도 삭제 대상이 되지 않는다 — Venue 도메인의 리뷰/직원평가/이벤트 이력이 영구 보존되어야 하기 때문 |
| Cleanup 범위 제한 | 기존 `delete_old_rooms()`는 `room_type = 'PERSONAL'` 조건이 추가되어, PERSONAL 방에 대해서만 기존 24시간/2일 정리 정책이 계속 적용된다 |
| **고정 QR 입장 (신규)** | BUSINESS 방은 참여자에게 `rooms.code`를 요구/노출하지 않는다. 참여는 매장(Venue)에 고정된 QR(=`venue_id`)로 이루어지며, 그 매장의 "현재 진행 중인 세션(가장 최근 `active` 방)"에 자동으로 입장한다. `code` 컬럼 자체는 내부 URL 슬러그(`/room/[code]`)로 계속 쓰이지만, 참여자가 직접 입력하거나 QR에 노출되는 값이 아니다 |
| **영업 시작 = 방 생성 (신규)** | 운영자가 "오늘 영업 시작"을 누르면 그 시점에 매장 이름으로 자동 명명된 새 BUSINESS 방이 생성된다(기존 "방 만들기" 화면에서 이름을 직접 입력하던 것을 대체). 이미 진행 중인 세션이 있으면 새로 만들지 않고 기존 세션을 그대로 반환한다(중복 시작 방지) |
| **영업 종료 = 방 마감 (신규)** | "영업 종료"는 기존 마감(`closed`) 규칙(위 표)을 그대로 따른다. 즉 삭제되지 않고 매장 이력으로 영구 보존되며, 운영자는 종료 직후 운영 리포트로 이어진다 |
| **영업일 귀속 기준 (Phase 5.5, 신규 확정)** | 매장의 하루 데이터는 실제 달력 날짜가 아니라 **그 방이 생성된(영업이 시작된) 요일과 날짜**를 기준으로 귀속된다. 예: 화요일 14:00 시작 ~ 수요일 04:00 종료 세션은 전부 "화요일 데이터"다. `rooms.created_at`의 날짜가 곧 그 세션의 영업일이며, Operator Analytics 도메인(§2.10)의 일별 집계도 이 기준을 그대로 쓴다 |
| **마감 시간 기반 자동 마감 (Phase 5.5, 신규 확정)** | 운영자가 "영업 종료"를 누르지 않고 방치해도, 매장의 요일별 설정 마감 시간(§2.2 "요일별 영업시간") **+1시간이 지나면 시스템이 자동으로 마감 처리**한다. 예: 화요일 14:00~04:00 설정 시 → 수요일 05:00에 자동 마감. 이 기준은 운영자가 직접 선언한 값(영업시간 설정)에만 근거한다 — 참여자 활동량으로 "조용하니 끝난 것 같다"를 추론하지 않는다(운영자·직원이 참여자로 위장 입장해 활동을 만들면 그 추론 자체가 무력화되기 때문) |
| **`closed_reason` (신규 확정)** | 마감된 방은 `closed_reason`으로 마감 주체를 구분한다 — `'operator'`(운영자가 직접 "영업 종료" 버튼을 누름) / `'auto_schedule'`(설정된 마감시간+1시간이 지나 시스템이 자동 마감). 자동 마감이어도 그 시간 동안의 참여자 상호작용 자체는 실제 데이터이므로, Operator Analytics 대시보드 집계에서 제외하지 않는다 — 감사/디버깅 목적의 구분일 뿐이다 |
| **크론 주기 (신규 확정, 임시)** | 자동 마감 판정은 하루 1회(새벽 5시) 크론이 일괄 처리한다 — Vercel 무료 플랜은 크론이 하루 1회만 가능하기 때문. 그래서 실제로는 "마감시간+1시간"보다 최대 24시간 늦게 정리될 수 있다(다음날 새벽 5시 배치 때 잡힘). 유료 플랜으로 올리면 크론 주기를 매시간으로 좁혀 정확도를 높일 예정이다 |

### 2.2 Venue 도메인

**정의**: 하나의 물리적 매장이 시간에 걸쳐 여러 방(세션)을 만들어도 유지되는 브랜딩·위치·설정을 책임진다. Room 도메인의 상위이자, Staff/Review/Discovery 도메인이 참조하는 최상위 엔티티다.

| 규칙 | 내용 |
|------|------|
| 방과 매장의 관계 | BUSINESS 방은 하나의 `venue_id`에 연결되며, 한 매장은 여러 방(세션)을 시간에 걸쳐 생성할 수 있다 (1 venue : N rooms) |
| 브랜딩 소속 | 매장명/로고/컬러/리뷰 URL은 Room이 아니라 Venue에 귀속되어 방이 바뀌어도 유지된다 |
| 방별 오버라이드 | 특정 방만 예외적으로 다른 테마를 쓰고 싶은 경우에 한해 `room_configs`로 개별 오버라이드 가능 (기본은 Venue 설정을 상속) |
| **입장 비밀번호 (신규)** | 운영자는 `join_password_enabled`(기본 false)로 입장 비밀번호 검사를 켜고 끌 수 있다. 켜져 있으면 참여자는 `join_password`(평문 저장, 형식 제한 없음 — 한글/영문/특수문자 혼용 가능)를 정확히 일치시켜야 입장 가능하다. 운영자가 자유롭게, 원하는 주기(매일/그때그때)로 바꿀 수 있다 |
| **입장 비밀번호 노출 범위 (신규)** | `join_password`는 그 매장의 운영자 본인 조회 응답에만 포함되고, 공개 조회·참여자 응답에는 절대 포함되지 않는다 (`operator_owner_token`과 동일한 노출 원칙) |
| **위치 반경 제한 (신규)** | `geofence_radius_m`(기본 50m)로 매장마다 입장 허용 반경을 갖는다. 참여자의 위치가 매장 좌표로부터 이 반경을 벗어나면 입장 자체가 거부된다 |
| **고정 QR 악용 방지 근거** | 매장 QR이 고정되면 "QR 사진을 유포해 실제 방문 없이 원격으로 도배"하는 악용 경로가 새로 생긴다. 입장 비밀번호(선택)와 위치 반경 제한(항상 적용)은 이 경로를 막기 위한 장치다 — Discovery 도메인의 "방 코드 비노출" 원칙과 같은 목적(실제 방문 검증)을 고정 QR 환경에서도 유지하기 위함 |
| **매장명 변경 금지 (신규 확정)** | `venues.name`은 최초 등록 시점에만 정해지며, 등록 이후에는 운영자 설정 화면에서 변경할 수 없다(API도 화이트리스트에서 제외). 향후 "실제 존재하는 매장인지" 검증하는 시스템을 만들 계획인데, 그 판정 근거가 되는 매장명을 운영자가 마음대로 바꿀 수 있으면 검증 자체가 무의미해지기 때문이다. 대신 오늘의 세션 이름(`rooms.name`, §2.1 "영업 시작 = 방 생성"으로 자동 명명됨)은 매장 정체성이 아니라 그날의 표시 이름일 뿐이므로 운영자가 자유롭게 바꿀 수 있다 |
| **요일별 영업시간 (Phase 5.5, 신규 확정)** | `venue_business_hours`에 매장당 요일(월~일) 7행을 둔다. 각 행은 `is_closed`(정기휴무), `is_24h`(24시간 영업), `open_time`/`close_time`, `last_order_time`(선택)을 갖는다. 정기휴무 체크 시 그 요일의 시간 입력은 비활성화되고, 24시간 체크 시 `00:00~24:00`이 자동 입력되며 마찬가지로 입력이 비활성화된다 |
| **영업시간 설정 필수 (신규 확정)** | 매장이 "오늘 영업 시작"을 누르려면 7개 요일 전부의 영업시간이 먼저 설정돼 있어야 한다 — §2.1 "마감 시간 기반 자동 마감"의 유일한 판단 근거이므로, 미설정 상태로는 그 자동 마감 자체가 불가능하기 때문이다. 오늘이 정기휴무로 설정된 요일이면 영업 시작 자체가 거부된다 |
| **라스트 오더 유효성 (신규 확정)** | `last_order_time`을 설정하면 그 요일의 영업 시작~종료 시간 사이(자정을 넘어가는 영업은 그 다음날 새벽까지 포함)여야 한다. 예: `14:00~익일 04:00` 영업이면 라스트 오더는 `익일 03:00`까지 가능 |

### 2.3 Participant 도메인 확장 규칙 (위치 기반 반경 제한, 신규)

**정의**: BUSINESS 방에서, 참여자의 실시간 위치가 매장 반경 이내인지를 입장 시점과 입장 이후 지속적으로 검사하는 규칙. 기존 B2C Participant 규칙(§1.2)은 전혀 수정하지 않고, BUSINESS 방에서만 적용되는 추가 규칙이다.

| 규칙 | 내용 |
|------|------|
| 입장 시 검사 | `POST /api/venues/[id]/join`은 참여자가 보낸 위경도와 매장 좌표 사이 거리를 계산해, `geofence_radius_m`을 벗어나면 입장을 거부한다 (403) |
| 입장 후 지속 검사 (신규) | 입장한 뒤에도 참여자의 위치가 주기적으로 재확인되며, 반경을 벗어나면 **자동으로 나가기(soft leave) 처리**된다. 이는 참여자가 직접 "나가기" 버튼을 누른 것과 동일한 처리(`left_at` 기록)이며, 별도의 삭제/차단 API가 아니라 기존 나가기 메커니즘을 자동으로 트리거하는 것이다 |
| 위치 정보 없는 매장 | `venues.latitude`/`longitude`가 설정되지 않은 매장은 반경 검사를 건너뛴다(제한 없음) — 위치 등록은 선택 사항이므로, 등록 안 한 매장의 입장 자체를 막지 않는다 |
| PERSONAL 영향 없음 | 이 규칙은 `venue_id`가 있는 BUSINESS 방에만 적용된다. PERSONAL 방은 Venue 자체가 없으므로 대상이 아니다 |

### 2.4 Staff 도메인

**정의**: 매장 소속 직원의 목록, 교대 근무, 참여자로부터 받는 친절도 평가를 책임진다.

| 규칙 | 상태 | 내용 |
|------|------|------|
| 직원 엔티티 | 확정 | 직원은 Venue에 귀속되는 정식 엔티티(`staff_members`)로 관리되며, 자유 텍스트가 아니라 목록에서 선택하는 방식 |
| 직원 명부 관리 위치 | 확정 (Phase 6) | 직원의 추가/삭제(명부 자체 구성)는 운영자 설정 화면에서 사전에 한다 — Seating의 "좌석 배치 구성"과 같은 패턴(구조 설정은 설정 화면, 실시간 개입은 방 화면) |
| 직원 삭제 방식 | 확정 (Phase 6) | `staff_members`는 하드 삭제 대신 `is_active`로 소프트 삭제한다 — 과거 교대 기록·친절도 투표가 그 직원을 참조하므로, 하드 삭제하면 지난 영업일 리포트가 깨진다 |
| 교대 기록 | 확정 | 교대 이벤트(`staff_shifts`)는 시작/종료 시각을 기록하며 삭제되지 않는다 (감사 이력 성격) |
| **교대 트리거 위치** | 확정 (Phase 6) | 직원 출근/퇴근(교대 시작/종료)은 별도 관리 화면이 아니라, 운영자가 영업 중 이미 보고 있는 **방 화면**에서 실시간으로 처리한다 — Guest Care(§2.9)의 "트리거 화면 위치" 원칙과 동일한 이유(운영자가 이미 보고 있는 화면에 개입 지점을 두는 것이 별도 화면 왕복보다 낫다) |
| 교대는 영업일(Room)에 귀속 | 확정 (Phase 6) | `staff_shifts`는 추상적인 시각 매칭이 아니라 `room_id`를 직접 참조한다 — 교대 시작/종료가 애초에 방 화면에서 트리거되므로, 그 시점의 활성 Room에 직접 귀속시키는 편이 간단하고 이 앱의 다른 모든 도메인(참여자/리액션/채팅)과도 일관된다 |
| 친절도 투표 1인 1표 | 확정 | Participant 1인은 Room 1회당 직원 친절도 투표를 1표만 행사 가능 (`UNIQUE(room_id, participant_id)`) |
| **친절도 투표 방식** | 확정 (Phase 6) | 별점(1~5)이 아니라 "가장 친절했던 직원 1명"을 고르는 단일 선택 투표다 — 집계는 득표수 기준 랭킹 |
| **투표 대상 직원 범위** | 확정 (Phase 6) | 참여자가 투표할 수 있는 직원은 그 Room 동안 `staff_shifts` 기록이 있던(그 영업일에 실제로 근무한) 직원으로 한정한다 — 그날 근무하지 않은 직원은 후보로 노출되지 않는다 |
| 투표 스킵 가능 | 확정 | 직원 친절도 평가는 필수가 아니며 스킵 가능 (기존 UX 흐름을 방해하지 않는다는 원칙과 일관) |
| 실명 미노출 | 확정 | 참여자의 투표 행위 자체는 Venue/Staff 도메인에 익명 집계로만 제공되며, "누가 누구에게 투표했는지"는 운영자 화면에 개별 노출되지 않는다 (랭킹/집계만 제공) |

### 2.5 Review 도메인 (검증 리뷰)

**정의**: 참여자의 실제 세션 데이터(Reaction 도메인)를 근거로 한 "조작 불가능한 방문 인증 리뷰"의 생성·공개여부를 책임진다. 새로운 입력을 받지 않고 기존 도메인 데이터의 스냅샷만 저장한다.

| 규칙 | 내용 |
|------|------|
| 생성 조건 | `venue_reviews`는 참여자가 실제로 QR 입장 후 세션 중 Reaction(별점/HOT)을 발생시킨 경우에만 생성 가능 — 임의의 텍스트 리뷰 작성 API는 존재하지 않는다 |
| 데이터 불변 | `satisfaction_snapshot`, `venue_hot_snapshot`, `visited_at` 값은 생성 이후 어떤 API로도 수정할 수 없다 |
| 운영자 권한 범위 | 운영자는 `is_hidden` 필드(공개/비공개)만 변경 가능하며, 이는 소프트 삭제로 처리된다 |
| 통계 정합성 | `is_hidden = true`로 숨긴 리뷰라도, Operator Analytics 도메인의 리포트 계산(`get_operation_summary` 등)에는 원본 데이터가 계속 포함된다 — 숨김은 "외부 공개 화면"에서만 제외를 의미 |
| AI 추론 금지 | 리뷰 문구, 코멘트 등 어떤 형태의 자유 텍스트도 AI가 생성하지 않는다. 오직 실제 발생한 수치의 스냅샷만 사용 |

### 2.6 Public Transparency 도메인 (실시간 공개 채팅)

**정의**: 매장이 opt-in한 경우에 한해, Chat 도메인의 데이터를 비참여자에게도 노출하는 규칙을 책임진다. 별도 테이블 없이 Chat 도메인 데이터를 조건부로 재노출한다.

| 규칙 | 내용 |
|------|------|
| 기본값 | `public_chat_enabled = false` (비활성화) |
| 활성화 권한 | 오직 매장 운영자만 Venue 설정에서 명시적으로 켤 수 있다 (opt-in, 참여자나 시스템이 임의로 켤 수 없음) |
| 고지 의무 | 공개 채팅이 활성화된 방에 참여자가 입장할 때 "이 방의 채팅은 외부에 공개될 수 있습니다" 고지를 표시해야 한다 |
| 노출 범위 제한 | 공개 API 응답에는 `sender_nickname`, `content`, `created_at`만 포함되며, 참여자의 개인 식별 정보(`phone_number` 등)는 어떤 경우에도 공개 API 응답에 포함되지 않는다 |
| 노출 대상 | 오직 `status = 'active'`인 방의 채팅만 공개되며, `closed` 방의 과거 채팅은 공개 API로 노출되지 않는다 |

### 2.7 Discovery 도메인 (주변 추천 / 실시간 HOT 랭킹)

**정의**: 참여자의 현재 위치를 기준으로, Venue + Room + Reaction 도메인 데이터를 조합해 실시간으로 분위기가 좋은 주변 매장을 찾아준다. 자체 저장 상태 없이 조회 시점에 계산한다.

**진입 경로 (v2 갱신)**: Discovery는 이제 두 가지 경로를 모두 가진다 — (1) 기존 설계대로 BUSINESS 방 참여자의 "방 나가기" 흐름에서 제공되는 다음 추천, (2) **앱의 기본 홈 화면**(지도 기반) 자체가 Discovery를 진입점으로 사용 — 로그인/입장 없이 누구나 주변 실시간 HOT 매장을 지도에서 먼저 보고, 그중 한 곳을 실제로 방문해야만 입장할 수 있다.

| 규칙 | 내용 |
|------|------|
| 대상 매장 조건 | 위치(위경도)가 등록되어 있고, 현재 `status = 'active'`인 방을 보유한 Venue만 랭킹/지도에 포함 |
| 정규화 원칙 | 단순 HOT 총량이 아니라 "현재 활성 참여자 수 대비 최근 N분간 HOT 발생 밀도"로 점수를 계산 — 대형 매장이 항상 유리해지는 편향을 방지 |
| 실시간 윈도우 | 기본 15분 이동 윈도우 내 HOT 리액션만 집계 (오래된 활동은 반영하지 않음) |
| 조작 불가 | 랭킹 점수는 실제 참여자의 HOT 탭(Reaction 도메인)에서만 산출되며, 매장이 직접 점수를 입력/수정할 수 있는 경로는 없다 |
| **방 코드/QR 비노출 (신규, v2)** | **Discovery 화면(홈 지도 포함)은 어떤 형태로도 방의 `code`나 QR 이미지를 응답에 포함하거나 화면에 노출하지 않는다.** 노출 가능한 것은 오직 매장명/카테고리/실시간 HOT 지수/평균 만족도/(opt-in 매장만) 공개 채팅 프리뷰뿐이다. 참여(join)는 반드시 해당 매장에 실제로 방문해 QR을 스캔해야만 가능하다 — 이는 "원격으로 코드만 알아내 실제 방문 없이 리액션을 조작·도배하는 것"을 구조적으로 차단하기 위함이며, Review 도메인의 "실제 방문 검증" 원칙과 근거를 공유한다 |
| 노출 범위 | 기본은 PERSONAL/BUSINESS 구분 없이 앱 전체 진입점(홈)에서 접근 가능. 단, 지도/목록에 표시되는 매장은 BUSINESS 방을 보유한 Venue로 한정된다 (PERSONAL 방은 애초에 Venue가 없어 대상이 아님) |

**지도 마커 상세 (바텀시트) — v3 갱신**: 홈 지도에서 마커를 탭하면 별도 페이지 이동 없이 지도 위에 바텀시트로 매장 상세를 보여준다. 이 바텀시트는 Discovery가 이미 노출하는 정보(매장명/카테고리/거리/실시간 HOT 지수/평균 만족도/opt-in 공개 채팅 프리뷰)에 두 가지 액션을 더한다 — **새 규칙이 아니라 기존 Room/Venue 입장 검증(§2.1~2.3)과 길찾기 UX를 지도 화면에 노출하는 진입점**이다.

| 규칙 | 내용 |
|------|------|
| 입장하기 버튼 | 바텀시트의 "입장하기"는 `/v/[venueId]` 참여자 랜딩 화면으로 이동시킬 뿐이다. 실제 비밀번호/위치 반경 검증은 여전히 `/v/[id]`와 그 join API가 수행하며, 바텀시트는 이 검증을 우회하거나 대신하지 않는다 |
| 반경 밖 UX | 매장까지의 거리가 그 매장의 `geofence_radius_m`를 벗어나 있으면 입장하기 버튼은 **비활성화**되고 "매장에서 OOOm 떨어져 있어요" 안내 문구를 보여준다. 이 표시는 UX 힌트일 뿐이며, 실제 반경 판정의 최종 근거는 항상 join 시점 서버 체크다 (지도 목록의 거리값은 목록을 불러온 시점 기준이라 약간의 시차가 있을 수 있음) |
| 길찾기 버튼 | 매장의 위경도로 외부 지도 앱(카카오맵) 길찾기를 연결한다. 별도 도메인 규칙이 필요 없는 순수 UX 기능 |
| /discover 리스트 페이지 | 그대로 유지한다. 지도(마커→바텀시트)와 `/discover`(카테고리 필터+정렬 리스트)는 서로 다른 탐색 방식으로 병행 제공 — 하나를 없애지 않는다 |

### 2.8 Seating 도메인 (좌석/자리배치)

**정의**: 매장 내부의 물리적 좌석 배치를 운영자가 구성하고, 참여자가 BUSINESS 방 입장 시 좌석을 선택하며, 운영자가 참여자의 좌석을 직접 옮길 수 있고, 좌석 단위로 실시간 HOT 활동과 착석 경과시간을 보여준다.

| 규칙 | 상태 | 내용 |
|------|------|------|
| 좌석 배치 구성 | 확정 | 매장(Venue) 운영자가 자기 매장의 좌석/테이블 배치를 구성한다 (Phase 2 브랜딩 편집기와 같은 "운영자 설정" 패턴) |
| 입장 시 좌석 선택 | 확정 | 참여자가 BUSINESS 방에 입장하면 자리배치도 화면으로 이동해 자신에게 맞는 좌석을 선택한다 |
| 좌석별 HOT 표시 | 확정 | 자리배치도에는 각 좌석에 앉은 참여자가 "지금 HOT을 탭하고 있는지"가 표시된다. `reactions`(hot)를 참여자의 좌석 배정과 조인해 계산하는 파생값이며, 좌석 전용 원본 데이터를 새로 만들지 않는다 (Atmosphere Index 도메인과 동일 원칙) |
| **운영자의 좌석 강제 이동 (신규 확정)** | 확정 | 운영자는 자리배치도에서 참여자의 좌석을 자유롭게 옮길 수 있다 (데스크톱: 드래그, 모바일: 롱프레스 2초). 이동 즉시 **해당 참여자 화면에도 실시간으로 반영**된다. 목적: 손님이 잘못 선택한 좌석을 운영자가 대신 수정 |
| **착석 경과시간 타이머 (신규 확정)** | 확정 | 좌석에는 그 참여자가 "이 좌석에 몇 시간째 앉아있는지" 경과시간이 표시된다. `seat_assigned_at`(좌석 배정 시각) 기준으로 매번 재계산하는 파생값이며, 원본을 별도로 갱신하지 않는다 |
| 좌석 이동 시 타이머 처리 | **미확정(해석 필요)** | "그 자리에 앉은 시간"이라는 문맥상, 운영자가 좌석을 옮기면 새 좌석 기준으로 타이머가 리셋되는 것으로 해석했다. 방을 나가지 않고 좌석만 바뀐 것이므로 "총 참여 시간"이 아니라 "현재 좌석 착석 시간"이라는 전제다 — 다르게 의도하셨다면 알려주시면 수정한다 |
| **좌석 선택 필수 여부 (확정)** | 확정 | BUSINESS 방은 QR 입장 직후 좌석 선택이 **필수**다 — 좌석을 고르기 전에는 방 화면(리액션/채팅)으로 들어갈 수 없다. PERSONAL 방에는 이 제약 자체가 없다 |
| **좌석 배치 자유 구성 (신규 확정)** | 확정 | 좌석은 `label` 하나로 목록에 순서대로 추가되는 방식이 아니라, `position_x`/`position_y`(캔버스 대비 0~100% 좌표)를 가져 운영자가 드래그로 실제 매장의 물리적 구조(테이블 배치)와 유사하게 배치할 수 있다. 참여자의 좌석 선택 화면과 방 화면의 자리배치도도 동일한 좌표로 렌더링되어, 운영자가 구성한 실제 동선을 참여자도 그대로 본다 |

### 2.9 Guest Care 도메인 (손님 케어) — 신규, 일부만 확정

**정의**: 운영자가 자리배치도에서 특정 손님을 지목해 개입하는 행위를 책임진다. 위치(Seating)와는 별개로, "그 손님에게 무엇을 하는가"만 다룬다. 사용자가 "앞으로 기능이 계속 늘어날 것"이라고 명시했으므로, 액션 종류를 쉽게 추가할 수 있는 확장형 구조로 설계한다.

| 규칙 | 상태 | 내용 |
|------|------|------|
| 트리거 방식 | 확정 | 자리배치도에서 손님을 우클릭(데스크톱) / 터치(모바일)하면 액션 메뉴가 뜬다 |
| **트리거 화면 위치 (수정)** | 확정 | 이 액션은 운영자 전용 별도 관리 화면이 아니라, **방 화면(참여자와 동일 화면)에 표시되는 자리배치도**에서 트리거된다. 운영자 설정의 "좌석 관리" 화면은 좌석 구성(추가/배치/삭제, §2.8 "좌석 배치 자유 구성")만 담당하는 구조 설계 도구이고, 손님에게 실시간으로 개입하는 행위(경고 메시지, 좌석 강제 이동)는 운영자가 이미 보고 있는 방 화면에서 바로 처리한다 |
| 운영자 경고 메시지 | 확정 | 자유 텍스트를 입력해 특정 손님에게 보낼 수 있다. **Reaction 도메인의 `warning`(자제 시그널)과는 다른 개념** — 참여자 간 익명 신호가 아니라 운영자가 특정 참여자에게 보내는 메시지다. 사용자가 "추후 추가 예정"이라고 했으므로 지금은 자유 텍스트 하나만 확정 |
| **경고 메시지 전달 방식 (확정)** | 확정 | 참여자 화면을 가리는 **모달/팝업**으로 표시되며, 참여자가 확인 버튼을 눌러야 닫힌다 (배너처럼 조용히 지나가지 않음 — 운영자 개입은 즉시 인지시켜야 함) |
| 쿠폰 지급 | **Phase 4 범위 밖으로 연기** | 등록 화면/데이터 구조, 수령 확인 방식이 모두 미확정이라 사용자가 이번 Phase에서 제외하기로 결정. 좌석배치+경고 메시지만 먼저 구현하고, 쿠폰은 사양이 확정되면 별도 Phase로 진행한다 |
| 확장성 | 확정 (설계 원칙) | 경고 메시지 외에도 앞으로 액션이 더 추가될 가능성이 높다고 사용자가 명시함 — 액션 메뉴/데이터 모델(`operator_alerts`)은 새 액션 타입을 쉽게 끼워넣을 수 있는 구조로 설계한다 (예: 액션 타입을 enum/문자열로 열어두기) |

**무결성 원칙**: 운영자 경고 메시지와 쿠폰 지급은 모두 **운영자가 특정 참여자에게 직접 개입하는 신규 쓰기 동작**이라, 기존 도메인들이 지켜온 "운영자는 원본 리액션 데이터를 수정할 수 없다"는 원칙과는 성격이 다르다 (Reaction 데이터를 건드리는 게 아니라 별도의 새로운 상호작용을 만드는 것). 다만 이 로그(누구에게 언제 무엇을 보냈는지)는 그 자체로 감사 이력이 되어야 하며, 삭제되지 않고 보존되어야 한다.

### 2.10 Operator Analytics 도메인

**정의**: 위 모든 도메인의 데이터를 읽기 전용으로 재가공해 대시보드/퍼널/리포트를 제공한다. `operation_events`(운영자가 직접 기록하는 타임스탬프 메모, Staff 도메인과 함께 Phase 6에서 다룸)를 제외하면 자체 쓰기 상태를 갖지 않는다.

| 규칙 | 상태 | 내용 |
|------|------|------|
| 원본 데이터 미수정 | 확정 | 대시보드/퍼널/리포트는 Reaction/Chat/Participant 등 다른 도메인의 데이터를 조회만 할 뿐, 어떤 값도 직접 쓰거나 수정하지 않는다 |
| **이벤트 기록 예외 (Phase 6, 갱신 확정)** | 확정 | `operation_events`는 사전 정의된 이벤트 타입 목록이 아니라, 운영자가 그 순간 남기는 **자유 텍스트 타임스탬프 메모**다 — "게임 시작"/"음악 변경" 등은 고정 타입이 아니라 그냥 메모 내용의 예시일 뿐이다. 이 메모만 이 도메인이 직접 쓰기를 소유한다 |
| **이벤트 노출 위치 (신규 확정, Phase 6)** | 확정 | 기록된 메모는 두 군데 모두에 노출된다 — (1) 그 영업일이 진행 중인 동안 **방 화면**에 실시간 목록으로, (2) 마감 후에는 **운영 리포트의 추이 그래프(TrendLine)** 위에 그 시각의 작은 마커로 표시되어, 마우스 오버(데스크톱)/터치(모바일) 시 메모 내용을 보여준다 |
| 운영 데이터 UI 고도화는 별도 예정 | 확정 | 필터링, 다양한 분석 방식 등 운영 리포트 UI 자체의 개선은 이번 Phase 범위가 아니다 — 지금은 메모를 기록하고 그래프에서 확인할 수 있게만 하고, 대시보드 UI 전반은 추후(피그마 리디자인과 함께) 별도로 손본다 |
| AI 추론 금지 | 확정 | 리포트/분석은 오직 저장된 이벤트만 근거로 하며, 저장되지 않은 상황(예: "단체 손님이 나갔다", "건배해서 분위기가 좋아졌다")은 어떤 형태로도 추론·생성하지 않는다 |
| **운영 리포트 대상 (Phase 5, 신규 확정)** | 확정 | 마감(`closed`)된 BUSINESS 방 하나하나가 "지난 영업일" 한 건이다. 진행 중(`active`)인 방은 아직 끝나지 않은 영업이라 리포트 대상에서 제외한다 |
| **HOT 밀도 (신규 확정)** | 확정 | 대시보드의 "HOT 밀도"는 방 화면의 실시간 HOT %(초 단위 감쇠 시뮬레이션)와 다른 값이다 — `그 영업일의 HOT 탭 총 개수 / 손님 수`로 정의하는 대시보드 전용 파생값. 지난 영업일들을 서로 비교하는 데는 이 밀도로 충분하고, 감쇠 시뮬레이션을 서버에서 재현하는 비용을 피한다 |
| **재방문 손님 정의 (신규 확정)** | 확정 | 같은 매장의 서로 다른 영업일(방)에 동일한 참여자 `session_token`이 다시 나타나면 "재방문"으로 센다. 새로운 개인식별 트래킹을 추가하지 않고 Participant 도메인이 이미 갖고 있는 값만 근거로 한다 — 브라우저를 바꾸거나 로컬스토리지를 지우면 다른 사람으로 집계되는 것은 알려진 한계다 |
| **운영자 참여 제외 (신규 확정)** | 확정 | 운영자가 "사장님" 닉네임으로 자기 방에 참여자로 입장한 행(§2.9 트리거 화면 위치 관련 기능)은 손님 지표(참여자 수, 재방문 등) 집계에서 제외한다 |
| **조회 권한 (신규 확정)** | 확정 | 대시보드는 그 매장의 `owner_id`와 일치하는 로그인 계정만 조회할 수 있다(Operator 도메인 §2.11과 동일한 권한 판정) |

### 2.11 Operator 도메인 (운영자 계정 — 정식 회원가입/로그인)

**정의**: 매장 운영자(사람)를 식별하는 신원 도메인. 지금까지는 `venues.operator_owner_token`(브라우저가 발급한 임의 UUID, `localStorage`에 저장)을 사장님 신원으로 대신 써왔는데, 이 방식은 브라우저 데이터를 지우면 자기 매장에 영구히 못 들어가고, 한 사람이 여러 매장을 가질 방법이 없으며, 토큰이 XSS로 탈취되면 그대로 도용된다는 문제가 있었다. 이 도메인은 그 신원 문제만 책임지고, "매장이 무엇인가"는 여전히 Venue 도메인 소관이다.

| 규칙 | 상태 | 내용 |
|------|------|------|
| 인증 수단 | 확정 | 이메일+비밀번호 회원가입/로그인은 **Supabase Auth**(`auth.users`)에 위임한다 — 비밀번호 해시·세션(JWT)·쿠키 관리를 직접 구현하지 않는다 |
| `operators` 프로필 | 확정 | `auth.users`의 각 계정에 1:1로 연결되는 얇은 프로필 테이블(`operators`)만 이 앱이 소유한다 (표시 이름, 연락처, 역할) |
| Venue 소유권 | 확정 | `venues.owner_id`가 `operators.id`를 참조하는 외래키다. 외래키 하나이므로 자연히 1(운영자):N(매장) — 프랜차이즈처럼 한 사람이 여러 매장을 갖는 걸 그대로 지원한다 |
| 향후 소셜 로그인 | 확정 (설계 근거) | 구글/카카오 로그인을 나중에 추가할 계획이 있어 Supabase Auth를 선택함 — Supabase가 두 프로바이더를 기본 지원하므로, 나중에 대시보드에서 켜기만 하면 되고 이 도메인의 스키마/코드를 다시 바꿀 필요가 없다 |
| 기존 토큰과의 관계 | **전환 기간 한정** | `venues.operator_owner_token` 컬럼은 즉시 삭제하지 않고, `owner_id`로 옮겨가는 매장별 "인증 전환"이 끝날 때까지만 남겨둔다. 전환 완료 후 컬럼을 제거한다 |
| PERSONAL 방과의 경계 | 확정 | 이 도메인은 BUSINESS(매장) 인증에만 관여한다. PERSONAL 방의 `host_session`(익명 브라우저 세션 토큰)은 이 리팩토링과 무관하며 그대로 유지한다 |

### 2.12 참여자 방 나가기(Exit Flow) — 도메인 간 순서 규칙

BUSINESS 방의 참여자 나가기는 여러 도메인에 걸친 아래 순서를 따르며, 각 단계는 스킵 가능(강제 아님):

```
만족도 별점 (Reaction 도메인, 기존 규칙 유지)
  → 직원 친절도 평가 (Staff 도메인, 신규, 스킵 가능)
  → 리뷰 유도 (Review 도메인, venue_reviews 자동 생성)
  → 주변 HOT 매장 추천 (Discovery 도메인, 신규)
```

PERSONAL 방은 위 순서 중 어떤 신규 단계도 노출되지 않으며, 기존 결과 화면 흐름을 그대로 유지한다.

### 2.13 도메인 횡단 무결성 원칙

- 운영자는 어떤 경우에도 **Reaction 도메인의 원본 데이터(hearts/warnings/stars/hot)를 직접 수정하는 API를 갖지 않는다**. 운영자가 통제 가능한 범위는 항상 "공개/비공개 전환"(Review 도메인의 `is_hidden`, Public Transparency 도메인의 `public_chat_enabled`)으로 한정된다.
- 파생 도메인(Atmosphere Index, Mutual Match, Discovery)은 원본 도메인(Reaction)의 데이터를 매번 재계산할 뿐, 별도의 상태를 저장하거나 운영자가 값을 주입할 수 있는 경로를 갖지 않는다.
- Review 도메인은 새로운 입력을 받는 도메인이 아니라 다른 도메인 데이터의 스냅샷 도메인이다 — 이 경계를 넘어 자유 텍스트 리뷰 작성 기능을 추가하지 않는다.

- 새로운 기능을 추가할 때는 먼저 "이것이 기존 도메인의 규칙 확장인지, 새로운 도메인인지"를 판단한 뒤 이 문서의 Part 0(도메인 정의)부터 갱신한다.
